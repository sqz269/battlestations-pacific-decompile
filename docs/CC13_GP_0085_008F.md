# CC13 gameplay bands 00850000-0087FFFF and 00890000-008FFFFF (cc13-gp85)

Packet `cc13-gp85`, Claude worker in the cc13 lineage, 2026-10-12. Gameplay code owned by cc9 (live,
approved cc13 metadata-plus-new-file passes). 00880000-0088FFFF was excluded entirely (cc9 shallow
water). This is a metadata pass plus a few build-tested leaves in a new cc13 band file. No host file
was edited, nothing was wired into a host and no game was run.

Names are hypotheses, not recovered symbols. Every ledger row (`config/names/0085..008f*.jsonl`,
evidence prefix `cc13-gp85`) carries its evidence: Lua binding rows, string immediates, vtable slots
read from the PE on disk with the slot meaning taken from peer vtables, IsKindOf class ids
(docs/ENTITY_CLASS_IDS.md), session message ids and the MT_ table at `00E0AB68`, and the caller spine.
Rows whose evidence starts with "Provisional" rest on body shape and caller context only.

## Method

- Input: `python tools/raw_ownership_cc13.py list cc9` filtered to the two bands: 566 functions
  (Ghidra `FUN_`, no tag, no ledger name). 549 had no export and were exported live first.
- Lua natives: the handler of each row of the binding table at `00E0B7B8` (`config/lua_bindings.json`)
  inside the bands; 214 raw handlers, each used by one row only, named `BSP_LuaBinding_<row name>`,
  the existing convention in these bands. Two more handlers that are not in the table were named from
  their `luaMW_<name> failed:` error strings (0089F360, 008CCEB0).
- Vtables: every absolute dword equal to a raw function was found in the non-code sections
  (`local/gp85_vtmap.py`), the table start found by walking back over code pointers, and the slot
  meaning taken from the names at the same slot in the entity vtables of docs/ENTITY_CLASS_IDS.md
  (`local/gp85_slothint.py`). Slot meanings used: +7Ch OnWrecked/OnKilled, +84h release
  sub-objects, +A0h SEntityInit/Activate, +A8h WriteState, +130h/+134h world-list register/detach,
  +17Ch send create message, +ECh apply hit record.
- The remaining 350 functions were drafted by four read-only helper agents in disjoint sub-ranges
  (00850000-0085FFFF, 00860000-0087FFFF, 00890000-008E2FFF, 008E3000-008FFFFF) with a common brief
  (`local/gp85_helper_brief.txt`) and reviewed by sampling before applying; the helpers wrote no
  ledger rows and made no Ghidra writes.
- Ghidra: renames and plate comments through `tools/ghidra_annotate.py --apply` under the write lock
  (prior state in `local/ghidra-annotations-20261012T222652Z.json` in the worktree).
- Generic containers use `STL_<op>_<addr>` and `TMPL_<container>_<op>_<addr>` ledger names.
  Functions with no direct call and no absolute reference carry the existing `_Unreferenced` suffix.

## Findings worth a second look

1. **Voice language bound is off by one.** `BSP_GameSettings_GetVoiceLanguageName` (008D57A0) tests
   `CMP [00F88978], index; JL english` at 008D57BE. `[00F88978]` is a count (the collector 008D76C0
   loops `i < [00F88978]` at 008D76F6), so index == count, and any negative index, read the row
   outside the table at `[00F88974] + index*20h + 10h`. `src/game_hosts_mission.cpp:677` still logs
   this function as unimplemented; the leaf below models it and returns nullopt for the out-of-table
   reads instead of reading.
2. **Ghidra boundary problems.** Two splits were repaired (see "Split repairs" below): 0085F7A0
   (`sub esp,44h; mov ebx,ecx`, the water mine's +7Ch OnWrecked, referenced from `00D0D1AC`) and
   008D9750. The rest are not repaired: 0085F2F0 (the water mine's
   message handler, `00D0D130` +164h: MT 0B5h arms the mine through 0085F1E0, else
   `BSP_BombProjectile_HandleMessage`) sits inside 0085F2B0. 008DAD70 (a `[ECX+28h]` getter) and
   008DAD80 (a session-message constructor installing `00D16024`) sit inside 008DAD30. 00861B10 (a
   float getter) and 00861B30 (a destructor storing `00D0D2FC`, then `BSP_CallbackOwner_Destroy`) are
   undefined code after 008619C0. 008E4B40, 008E4B60 and 008E4B80 (power-up slot record tests: ready,
   ready time, ...) are undefined code after 008E4B00. `scan-bytes` credits stores in those pieces
   to the wrong function.
3. **Gun-bot vtable starts differ by family.** The lead (`00D18088`) and ballistic (`00D18220`)
   table addresses used so far sit 18h before the destructor, while torpedo, depth charge and turret
   tables start at it, so the same virtual appears at +48h in one family and +30h in the other.
   The ledger names compare the families by body, not by slot.
4. **Possible naming mismatches in existing rows.** Vtable `00D1629C` is written by the function
   already named `BSP_PowerupConfig_Construct`; the helper rows call the same object (at
   `00F88C30`) `BSP_PowerUpManager`. Vtable `00D16038` is installed by `BSP_Objective_Construct`
   but its slots are named `BSP_SessionMessage55Entry_*` (the read slot reads "text", "quiet",
   "type", "state", "positions"). `BSP_Landscape_LocalHeight` (00ADA160) and
   `BSP_Landscape_LocalNormal` (00ADA1C0) belong to the height field (vtable `00D5D350`). The
   water mine's +84h ends in `BSP_MDestroyer_ReleaseSubObjects`, which looks shared. None was
   renamed here.
5. **Unreferenced code.** No call and no absolute reference (PE scan with a positive control):
   00851E40, 00851EE0, 00855FE0, 008580C0, 008580E0, 008583D0, 00858660, 0085BD50, 00861970-008619C0,
   00863130 (the gunnery property loader; odd for a live function, maybe reached through an
   unmapped vtable), the `BSP_RobotConfig_*` constructors and destructors, 008FF640, 008FB530,
   several identical map-init and container copies.
6. **Two RNG notes for the RNG rule.** None of the reconstructed leaves draws random numbers.
   `BSP_Powerup_PickFromBracketList_Provisional` was not audited for its stream.
