# CC15 G24C: audited game-code rows (narrative list, objective, node append)

Packet cc15-g24c. The cc15-stlA audit (docs/CC15_STL_PROBABLE_AUDIT.md) moved
these five rows from `stl_probable` to game code. Bodies are in
`src/cc15_g24c.cpp` / `include/bsp/cc15_g24c.hpp` (namespace
`bsp::cc15_g24c`). Names are hypotheses. Every call goes through a host seam;
fields are read and written as native Win32 layouts. Status: reconstructed and
build-tested only. No host calls these bodies, nothing is ABI-compatible and
nothing is game-validated.

Before writing, `git grep` over include/ and src/ found seams but no bodies:
`narrative_list_append_00734870` (cc13_front3.hpp, cc13_seg48U.hpp),
`client_007349c0` (engine_seg4_6_9_cc13.hpp), `show_message_00734e50`
(mission_state_frame.hpp, a higher-level seam that takes a text key only),
`objective_erase_position_entries_008dc500` (objectives_seg57_argon.hpp) and
`node_append_children_by_name_007d05e0` (cc13_seg47b.hpp). Each body's
argument list follows the matching seam, so a host could implement that
virtual by calling it. NativeString arguments are `const void*` pointing at a
{length, data} image, which is the same as `NativeNarrowString`.

## Narrative list layout

The narrative object (game+21E8h) holds a VC9 `std::list` at +4h: head +8h,
size +0Ch. Each node is {next, prev, entry}. The 18h-byte entry is {vtable
00CFE960, key NativeString, text NativeString, int}. The node's key starts at
+0Ch, its text at +14h and its value at +1Ch.

All three writers do the same inlined insert. They build a stack entry
{00CFE960, 0, 0, 0, 0, 0}, call 007342B0(ECX = list; next, prev, &entry)
→ node, and call 007341B0(ECX = list; 1), the size increment that throws on
overflow (ledger name `STL_xlen_throw_007341b0`). They then store
`where->prev = node` and `node->prev->next = node`, and destroy the temporary
with 00733DC0. Each string copy skips self-assignment. Otherwise it calls
0041DD40(dst; src.length, 1), re-reads src.length, and, when that is non-zero,
copies `dst.length` bytes with _memcpy (00BF7680), using the length after the
resize. The int goes to +1Ch last.

|---|---|---|

| 007349C0 | same, RET 0Ch, SEH 00C85DA8 | If the size is non-zero: front-not-head test, then 00435C40(front+0Ch, key). ## 008DC500 BSP_Objective_RemovePositionEntries

`__thiscall(ECX = objective; const float pos[3])`, RET 4, no SEH frame. It
walks the VC9 list at +20h (head +24h, size +28h). Each node holds a pointer at
+8h to a record {int kind, float x, y, z}. The walk re-reads the head word at
each point where the image does. EDI, the iterator's container, is always the
list, so the container test at 008DC511 fails only for a list at address 0.
Each float is compared with FUCOMIP, LAHF, `TEST AH,44h` and JP. That means
"ordered and equal": a NaN never matches, which is what C++ `==` does. When
kind == 0 and x, y and z all match, the function frees the record (_free
00BF65AC) and zeroes the slot. It then unlinks the node (skipped when the node
is the head), frees it and decrements the size. Otherwise it moves to the next
node.

## 007D05E0 BSP_Node_AppendChildrenByNamePrefix

`__fastcall(ECX = node, EDX = const char* name; vector*)`, RET 4, SEH
00C8CF48. It calls 0071BA20(ECX = node; &local10h, name). ECX goes through
untouched, so the call uses the entry node. It then loops over the local
vector (+4h first, +8h last), whose words are re-read from the stack on each
pass:

- If `first` is null, it returns without freeing.
- If index ≥ size, it frees `first` and returns.
- Otherwise, if the argument vector has a non-null begin and size < capacity,
  it stores the element at last and advances last by 4.
- Otherwise it runs the end-iterator test (begin > last, unsigned, at
  007D0661), then calls 00505D50(ECX = vector; &result, vector, last,
  &element).

## Limits and uncertainty

- EH unwind paths are not modelled. These are the temporary-entry destruction
  if 007342B0 or 007341B0 throws, and the local-vector destruction in
  007D05E0.
- The 007D05E0 local vector and the 00505D50 result iterator are
  zero-initialised in C++. In the image they are uninitialised stack that
  0071BA20 or 00505D50 writes.
- Calls to 00BF6713 are modelled as a seam call that falls through, as in the
  image.
- The roles of the narrative entry fields (key, text, value) come from their
  callers: Lua MissionNarrative* and the latency/player-count warnings. The
  host's `NarrativeEntry` names them text/callback/arguments. The field names
  are provisional.
