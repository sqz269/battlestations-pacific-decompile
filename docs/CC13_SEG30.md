# cc13-seg30: segments 30 and 50

Packet `cc13-seg30` (2026-10-14). Segment 30 is `006BEB70..006D4340` (the air-ops block, its landing
sites and the `MAirfield` unit); segment 50 is `0080DA00..0081AA10` (unit-instance helpers, the ship
session messages, the helmsman estimator). The pass took the 179 + 94 functions that had no
reconstruction record.

Status vocabulary: everything listed under "Reconstructed" is reconstructed and build-tested. None of
it is ABI-compatible, fixture-tested or game-validated, and none of it is bound into `bsp_game`.
Names are hypotheses, not recovered symbols.

## Model

`include/bsp/cc13_seg30.hpp` declares every routine in `bsp::cc13_seg30`. The code is in
`src/cc13_seg30.cpp` (segment 30) and `src/cc13_seg30_seg50.cpp` (segment 50). Each routine works on
the original object as raw bytes, with offsets as in the image. Every engine call goes through
`Seg30Host` / `Seg50Host` (segment 50 extends segment 30). Each host method is named after the image
routine or virtual slot it stands for, and its comment gives the register inputs. Calls between
routines that are reconstructed here use the C++ directly (for example `006D0470` calls
`air_ops_site_destruct_006ceb70`). Constants carry their image address and width in the header.

Common simplifications, also stated per routine:

- x87 arithmetic is written in `double`. Every float product used is exact in `double`. A sum or
  quotient can round twice where the image rounds once from extended precision.
- The engine's tracked lock (`EnterCriticalSection` followed by `+18h += 1`, and the reverse) is the
  `lock_enter` / `lock_leave` pair.
- The debug-checked list iterator `{container, node}` is `CheckedIter`. The archive's tagged by-value
  argument `{kind, value}` is `ArchiveArg`.
- Copies that the image makes with x87 `FLD` / `FSTP` float pairs are written as plain float or dword
  copies. These differ only for a signalling NaN.

## Adoption notes

1. **Runway and hangar failures never close the launch gates in the host.** `006BF620` (inlined
   in `air_ops_is_ready_to_send_planes_00895d20`) reads the air-ops block's `+1Ch` / `+1Dh`. On an
   airfield or a carrier the block is embedded at `+72Ch`, so these are the unit's `+748h` / `+749h`,
   the bytes the Lua `GetFailure` reads. No code in `src/` ever sets `deck.runway_failure` or
   `deck.hangar_failure`. `FailureBinding::name_of` maps only effects 1 to 4 (Explosion,
   SteeringJam, EngineJam, Fire), and `apply_failure_effect_00827b90` ignores any other name.
   - What the image does: `SetFailure(unit, "RunwayFailure" | "HangarFailure")` routes message
     `72h` / `74h` (`0077C2A0(msg, 7, 0)`). For an airfield this happens in `006D2210..006D233E`,
     and for a carrier in `00758750` BSP_MotherShip_ApplyFailureByName (segment 41, under the
     argon-v2 lease).
   - Is it live: this installation's `scripts/datatables/shipglobals.lua` defines the `runway` and
     `hangar` damage sections with `FailureName` `RunwayFailure` / `HangarFailure` and
     `FailureDuration` 20. Missions also call it: `bsm_09_battle_of_the_coral_sea.lua:1203`
     `SetFailure(Mission.Lexington, "RunwayFailure", 180)` and `ijn/ESMP/03_south_pacific.lua:1246`
     `SetFailure(Mission.Zuiho, "RunwayFailure")`. So the path is live for carriers that take hits
     in those sections.
   - Not traced: the carrier-side handler that would set `+748h` / `+749h`. A byte scan finds no
     `MOV byte [reg+748h], 1` and no `MOV [reg+748h], r8` that sets either byte (the writers found
     are constructors, `006D31A0` RestoreFullHealth and `0081C550`).
   - Shared RNG `00BD2F10`: the component-failure roll already draws in the host
     (`Draw::component_failure`). Applying the failure would not add draws. It would change launch
     timing, and that couples into later draws through the aircraft.
2. **The airfield's own failure messages clear the byte for both SET and CLEAR.** `006D2910`
   dispatches types `72h` / `74h` to vtable `+204h` and `73h` / `75h` to `+208h`. The `MAirfield`
   vtable `00CF8C08` holds `006D0D50` at `+204h` and `006D0D90` at `+208h` (bytes at `00CF8E0C`).
   Both routines store 0 to `+748h` / `+749h`. In the image, then, a SET message received by an
   airfield clears the failure. Together with the scan in note 1, this means an airfield's runway
   failure is probably never set in the image. In that case the host's never-set flags agree with
   the image for airfields, and the gap in note 1 is a carrier-only gap. This is reconstructed as
   the bytes read (`air_field_clear_failure_flags_on_set_006d0d50`). Whether it is an original bug
   or an undo path is not established.
3. **Catapult launch quirk (`008141E0`).** The function has several catapults, and none of them is
   within 10.0 (`00CE38B8`) of the requested heading. In that case the image calls `006EB680` with
   `ECX` = the raw bits of the float `heading` argument, because `EDI` is loaded from that stack slot
   (`008142B7`). The reconstruction keeps this. Whether a host launch path reaches it was not
   checked. `src/air_operations.cpp` and the ships host were not edited.

4. **The HUD torpedo-stock gauge source answers 0.** `src/game_hosts_hud.cpp:2501`
   `unit_torpedo_stock_00815850` records the call and returns 0. The image (`00815850`) returns
   `ship+104Ch`. When that is not negative, it adds `00810E90()` (a count over the `+3ECh` device's
   barrels, compared against the double at `00D7A278`). This is presentation only: no gameplay
   reads it, and it does not touch `00BD2F10`.
