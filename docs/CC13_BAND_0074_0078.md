## Session-message classes (237 names)

Every network message is a class with a five-slot vtable: scalar deleting destructor, Write (+4),
Read (+8), IsType (+0Ch) and slot 4 (`BSP_SessionMessage_AlwaysTrue` 004499C0 for all seen here).
The type byte lives at `msg+10h` and indexes the 235-entry name table `00E0AB68` (`MT_INVALID` ..
`MT_LAST`, docs/CC13_MULTIPLAYER_SESSION.md). IsType compares the class type first and then its base
types: for example `00741420` accepts CFh, 47h, 46h, which is `MT_LANDCONVOY_CREATE` ->
`MT_CREATE` -> `MT_NETENT`.

New names use `BSP_SessionMessage_<MT name>_<Slot>`. Older names in the image use
`BSP_SessionMessage<decimal type>_<Slot>` (for example `BSP_SessionMessage17_Construct` is
`MT_LETSPLAY`, 11h); those were not renamed.

- Batch 1 (202 names, commit 0872726d8): classes found from their constructors
  (`local/sw74_msgscan.py`): the last vtable store before RET plus the `MOV byte [reg+10h], imm`
  type store. For every named class the IsType slot's first constant equals that byte, except
  `0075C680` (`MT_PLAYERINFO`, E3h), whose IsType is the generic `BSP_SessionMessage_TypeEquals`.
  Cross-check: `MT_MUSICCONTROL_SETLEVEL` (2Ah) is vtable 00D0319C, the same one that
  `luaMW Music_Control_SetLevel`'s sender `0076D280` builds by hand.
- Batch 2 (35 names, commit 989510da6): vtables found by slot 4 = 004499C0 whose class has no
  separate constructor (built by `BSP_SessionMessage_ConstructBase` plus a vtable store). The type is
  the IsType slot's first compare.
- ICF check for both batches: every named slot function is referenced (whole `.rdata`/`.data`
  dword scan) only from message-vtable slots, the second batch only from its own slot, and none has
  a direct caller except the constructors.
- Scalar deleting destructors keep their template tags (`CG_scalar_deleting_dtor_*`).

## MNetwork transports (segment 43)

The XLive transports named by cc13-sweepA1 derive from two abstract bases here:

| vtable | class (provisional) | constructor | destructor |
|---|---|---|---|
| 00D04274 | MNetwork (slots 1, 3-5, 7-9 `__purecall`) | `00784F90` | `007844E0` |
| 00D042A0 | MNetworkClient | `00785B80` | `00784D60` |
| 00D042EC | LAN host record (std::string +8h, 88h-byte blob +20h) | not seen | `00784E00` |

MNetwork fields: `+4` owner (its vslot 0 judges each received message: 0 queue, 2 delete), `+0Ch`
peer list, `+1Ch` removal queue, `+2Ch` incoming peers, `+3Ch` received messages, critical sections
`+24h`/`+34h`/`+44h`, `+48h` removal timer (30.0 from 00CE38C8), `+8Ch`/`+90h` received byte
counters by packet kind, `+9Ch` state (client: 1 constructed, 2 after open/disconnect, more than 6
connected, 8 in play per the multiplayer doc). The client adds the host vectors `+A0h` (known hosts)
and `+B0h` (pending LAN results) under the `+C0h` lock.

Packet receive `00785A6F..00785AA0` unwraps the 16-bit tick against `00F876B0` (reconstructed
below). Message flow: XLive packet handler -> `BSP_MNetwork_ReceivePacket` -> owner verdict ->
`+3Ch` queue -> `BSP_PeerManager_PumpMessageQueues`.

## Session peer rows (MMultiPlayer+8h)

Eight 1Ch-byte rows (layout in `include/bsp/band_0076_cc13.hpp`) maintained on the host:
`BSP_GamePeerRows_AddPeer`/`RemovePeer` from the peer add/remove paths, `EnableProbes`/
`DisableProbes`, and `BSP_GamePeerRows_Update` (`007866B0`), which sends `MT_CONNTEST` (0Fh) probes
at a rate of quality / 0.09 s per stream (two streams, payload sizes 4Bh and 8Ch), refreshes the row
quality from the transport's latency and pending count every 0.2 s, and broadcasts `MT_CONNSTATE`
(10h) when its accumulator reaches 0.5. `BSP_Session_AveragePeerQuality` (cc13-net2) reads the same
quality field.

## Network packet statistics (segment 44)

The singleton at `00F871B4` (vtables 00D04318 base, 00D04388 full) records every packet the network
console sends (`BSP_NetworkPacketStatistics_RecordSent`, from `BSP_NetworkConsoleSend_SendWorker`)
and receives (`..._RecordReceived`), skipping the 8-byte header. The Lua binding `0088D6E0`
("luaMW_NetworkLog failed:") starts CSV logging (`..._StartCsvLog`): file names are
`ns_<name>_<server|client>_<send|recv>_<date>.csv`. `BSP_Game_Render` calls `..._FrameUpdate`, which
every fifth frame aggregates the per-type counters for types 1..E9h and writes a row
(`..._WriteCsvRow`, "Time;" prefix, columns ";%s;%d;%d").

3. The client arm of `BSP_Session_UpdateStartGate` and the remaining codes of

4. Whether `00782880` (client slot 1: Open, then state 2) and cc13-sweepA1's
   `BSP_MNetworkXLive_ShutdownToState2` (server slot 1: StartHosting, then state 2) are the same
   virtual (for example "Start"); the A1 name may be worth revisiting.

   Correction (cc13-stlreview1, 2026-10-12): answered in `docs/CC13_BAND_0080_008F.md`. The two
   slot +4 bodies are byte-identical overrides of the same virtual. `00A41300` belongs to the
   abstract server class and its `+28h` call starts hosting, so the A1 name
   `BSP_MNetworkXLive_ShutdownToState2` was replaced with
   `BSP_MNetworkServer_StartHostingAndSetState2`. The client name `BSP_MNetworkClient_OpenAndSetState2`
   (`00782880`) stands. The meaning of state 2 is still undecoded.
