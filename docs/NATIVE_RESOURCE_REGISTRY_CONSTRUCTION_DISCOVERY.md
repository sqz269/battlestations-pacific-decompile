## Sentinel and constructors

B19C30 consumes no incoming ECX or stack argument and returns EAX with plain RET. It calls actual operator new with **1Ch**, then conditionally writes link+0=0 if EAX is nonnull. It forms EAX+4, tests that current arithmetic result, conditionally writes parent+4=0, then repeats at EAX+8. Finally it writes byte+18=1 and byte+19=0. It leaves +0Ch..+17h payload and +1Ah..+1Bh padding unwritten. The null/addition branches must remain actual 32-bit operations: a returned null would skip only the first store and then fault at address4, not become an accepted empty sentinel. The canonical allocation provider uses actual malloc/new-handler behavior; this discovery does not claim an allocator-failure runtime case.

B1AA70 has native ECX=raw owner, EAX=same owner, RET. The reached owner prefix is 16 bytes: profile+0, **preserved DWORD+4**, tree head+8 and count+0Ch. It captures this in EDI and the unwind stack spill, sets ESI=this+4, arms state0 at B1AA93 **before** storing D5E594 at B1AA9B and before calling B19C30. No base-constructor call, zero-filled owner, string key or factory construction is implied.

On allocator return it writes EAX to current owner+8, sets returned node byte+19=1, then separately reloads owner+8 before each link store: node+4=self, node+0=self, node+8=self. It returns this in EAX and writes count+0Ch=0. The repeated head loads and store order are part of the raw contract, including overlaps; do not replace them with a single cached node or broad memset. The sentinel's color byte remains1. Its key/factory/padding bytes remain unspecified; the sentinel's nil identity keeps those bytes outside ordinary value-node key release in the completed tree destruction.

Constructor EH is fully identified. CBC6B8 is the FH3 handler stub, loading FuncInfo DF4994 and tail-jumping BF6B43. Its one-entry unwind map at DF498C is `state0 -> -1, CBC6B0`; that action reloads the owner from `[EBP-10h]` and jumps to **completed B19760**. B19760 clears the actual F8D41C publication and then stores CE3818 on that owner. A failed standalone constructor therefore clears that borrowed publication even before this owner has been published. No sentinel free is added to this action. A source packet may use the existing reset provider with an explicit stable actual publication reference and ordinary source exception cleanup; it must not claim original FH3/SEH stack compatibility, mutable EH spill alias behavior, or automatic cleanup after arbitrary hardware faults without separate proof.

B1B6E0 saves ESI, captures ECX, calls the whole B1AA70, writes D5E59C on the captured owner only after normal return, returns that owner and restores ESI. There is no extra outer EH action. The standalone base B197E0 simply stores D5E550 at raw+0 and returns ECX in EAX; it needs no allocator or lifetime service.

The separate B197F0 scalar reads **bit0 of the current low-byte flags slot before any publication/profile writes**, then saves ESI and captures ECX. It neither destroys a tree nor calls B1B5F0. It is not interchangeable with the completed registry scalars, which destroy the registry first and test flags afterward.

## Full getter order and unwind ownership

B1B730 is a cdecl-like no-input/EAX-result/RET getter with an original FH3 frame. Its fast path loads F8D41C once and returns that captured nonnull value, without touching manager, lock or allocator. On a miss it calls 415350 and captures **raw manager+10h** into ESI; no null-manager check exists. It writes an eight-byte stack guard (profile CE37FC, captured actual section pointer). If the captured pointer is nonnull, it calls actual EnterCriticalSection and only afterward increments the section's current physical DWORD+18h. The actual imported APIs are confirmed through CE2218 and CE2210.

State0 is armed only after that entry/increment. The getter rereads current F8D41C under the captured lock. If another publication is now present, it skips allocation and registration. Otherwise it allocates exactly10h, captures EDI and writes the separate raw allocation spill, then arms state1. A nonnull allocation receives full B1AA70 followed by the captured EDI profile store D5E59C; a null result retains the original null path. The source allocator contract remains the actual throwing new-handler service, not an always-success or nullable allocation policy.

State returns to0 **before** publishing EDI to F8D41C. The getter then calls 415350 again and only after that return reloads current F8D41C as the registration argument. Registration therefore receives the current publication, which need not equal the captured allocation. It does not retain/increment a registry refcount. A registration exception leaves the published owner in place; there is no rollback or owner-free state remaining.

Normal exit decrements the captured section's current +18h, then calls actual LeaveCriticalSection, while state0 remains armed. Final EAX reloads F8D41C **after Leave returns**. It does not return the captured allocation or the earlier under-lock publication. The source must preserve capture versus current identities through those calls.

The getter's handler CBC7C3 loads FuncInfo DF4B38 and jumps BF6B43. Its map DF4B28 has `state0 -> -1, CBC7B0` and `state1 -> 0, CBC7B8`. State1 first reloads the current allocation spill `[EBP-18h]`, passes it to actual free, and returns through POP ECX/RET; unwinding then reaches state0. State0 forms `[EBP-14h]` and calls completed raw guard destruction 411EE0. That provider captures guard+4, rewrites guard profile CE37FC, decrements the captured actual section's current +18h and leaves it without clearing guard+4. If B1AA70 itself throws, its reset action happens before these outer allocation/guard actions. No cleanup is armed during EnterCriticalSection or its post-call increment.

## Lifetime representation and remaining boundary

Current `SingletonLifetimeDomain::get_manager_00415350` and `ConcreteSingletonLifetimeManager::register_object` are completed **typed** implementations with an explicit host layout. Their actual source contains a virtual manager, callback storage, pointer slots and an `OwnedCriticalSection` projection; that object is not the raw original 14h-byte manager and cannot be cast to read native+10h. The original BD0960 zeroes only +4/+8/+0Ch, leaves +0 untouched, reserves256 and stores its actual tracked section at +10h.

For a fully raw manager migration, named blockers remain: BD0600 reserve is only a constructor-empty-vector fragment; BD08D0's foreign-owner iterator branch is omitted from the typed append-only contract; BD0BC0/BD0C30 expose typed manager storage; 415350/BD0960 remain typed getter/constructor providers. These labels do not close the raw ABI. Raw tracked-section creation BD1860 is already complete in `native_renderer_worker_lifetime.cpp`, and guard destruction 411EE0 is complete in `native_diagnostic_sink_lifetime.cpp`; do not list them as missing.

A narrower rebuilt-source getter composition can follow the already completed diagnostic getter 4C14C0: borrow the one existing actual `SingletonLifetimeDomain`, call its getter, use `system_owner().section_10` only as a documented projection, then obtain the **actual native section** through `projection->native_section`. Construct the raw eight-byte guard from that actual section; use the physical +18h counter and real OS calls. Do not call typed `manager.lock()` in addition, which would increment twice. The second manager lookup and current publication argument to its direct `register_object` must remain separate. This is an explicit representation adapter, not a raw-manager closure or a new private lifetime domain.

The existing domain requires a persistent `SingletonLifetimeCallbacks` registration/invalid-parameter contract. A future registry getter context must refer to the already-owned domain and actual F8D41C, with the registered owner dispatch concretely admitting the actual reached D5E59C/B1B710 (or separately justified D5E594/B1B660) identity and routing to the completed registry deletion provider with flag1 and actual pool/publication bindings. The actual pooled-string provider is needed for populated destruction, **not sentinel allocation or construction**; factory+14h values remain unowned by that destructor.

No registry-specific atexit registration appears in the complete getter, constructors or manager getter.
