`NativeParticleModelConstructionCallees::renderer_virtual5c` has a complete existing
Source provider and a concrete canonical application service domain. **A dormant
forwarding binding is not ready:** the particle path has no persistent stream
acquisition record or connection between such an interrupted operation and the
renderer failure-retention gate. This packet documents that exact prerequisite;
it adds no application state, C++, Native body, build, test or runtime execution.

## Why forwarding alone is insufficient

1. The adapter requires a fresh `NativeStreamCloneAcquired`, marks `factory`, and
   passes its creator slot into B287C0. The completed creator is published there
   **before** either renderer-array append.
2. B287C0 appends to captured renderer+1AAC, then additionally to +19B0 only when
   current virtual+58's secondary-registration byte is exactly1. A later throw can
   leave completed native work and partial registration. Constructor unwind also
   does not justify assuming that every earlier side effect was rolled back.
3. The adapter marks `registration`, allocates a stable geometry entry and a
   `NativeLogicalVertexReference`, then binds it into the canonical registry.
   Host allocation or binding may throw after native creation. The companion borrows
   the actual +04 count without retaining it; failed registration is not permission
   to recreate, release, erase native effects or retry the operation.
4. Only a successful adapter return hands out one registered creator reference.
   `finish_mesh` sets mesh slot0, drops that creator, then performs layout and section
   work. The eventual owner must cover failures through the actual handoff and later
   constructor unwind; the callee alone cannot infer that all references were retired.

The actual particle callee interface has no acquisition-output argument, no concrete
owner, and no retained particle stream record. The full Source query finds records
for other producers, which cannot be borrowed as this operation's state. A local
record would lose partial-effects evidence on throw. Even `creator == nullptr` is
not sufficient to erase an entered operation or declare it safe to repeat.

`GameNativeRendererApplication::requires_process_retention()` currently checks the
application phase, shader/shadow state, and section-layout acquisition/live companions.
It has no particle stream attempt. Calling a borrowed free function does not change
the application's phase. The existing application already uses ready -> operation ->
ready/failed transitions, and `GameStartupHost` already checks renderer retention
before draining. Future work must connect a persistent particle operation to this
existing mechanism; no extra failure flag is presumed necessary, and none is added.

The smallest next implementation prerequisite is therefore **persistent per-attempt
acquisition ownership, successful creator handoff, and failure-retention integration
inside the actual application/callee owner**. Once reviewed, the existing adapter and
borrowed graphics domain can supply this method. This packet does not claim that a
bare forwarding method, stack acquisition temporary, or dormant partial class may
proceed now.

All remaining methods stay unimplemented: `bind_particle_profile`,
`retire_failed_particle_profile`, `bind_mesh`, `bind_material`, `bind_section`, and
`call_00bd2f10`. The latter has separate accepted provider-readiness evidence, but the
whole callee remains abstract. No model activation follows from either packet.

## Static startup, publication and terminal lifetime

The existing `GameNativeGraphicsPoolProcess` owns graphics storage and borrows the
same E188B4 allocator-list domain. `initialize_once(logical_vertex)` binds its index4
logical pool, calls CD7C60 initialization, then records the actual atexit result and
returned state. CD7C60 initializes before registering CE0D20. A nonzero registration
result does not undo initialization or manufacture a second cleanup path. The
logical-pool getter requires returned state; startup failure and CRT teardown are
not reset/retry opportunities.

WinMain runs the existing graphics-pool sequence before creating `GameStartupHost`.
The renderer application first composes borrowed host metadata. B25F40 publishes the
renderer during construction, so a nonnull renderer is not ready-state evidence.
Actual device startup later allocates and publishes the shared physical vertex owner
at +1974, and the application reaches ready only after successful startup. No new
static initializer, publication cache or pool is required by the selected method.

The original application, service contexts, registry and mapped cells must outlive
every successful stream and interrupted acquisition. Complete stream retirement
uses the actual logical owner/physical services and then removes its canonical
companion. Finish borrowers and owners before renderer singleton drain and the
logical-pool CE0D20 callback. Existing host destruction retains interrupted native
state before drain; it does not yet know about this unimplemented particle operation.
No live startup, graphics, callback-reentrancy or concurrent-use guarantee is claimed.
