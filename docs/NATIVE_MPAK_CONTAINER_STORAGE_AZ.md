# MPAK actual container storage (AZ)

`NativeMpakContainerStorage` supplies the seven `NativeMpakContainerLibrary` methods used by the actual MPAK parser and provider teardown. It borrows the existing string storage, adopted-stream dispatch, allocator/pool service and BB6180 offset-vector copy library. The three vectors retain their actual 10h headers: opaque allocator word at +0 and begin/end/capacity at +4/+8/+C. File records remain 24h with untouched padding and allocator word +14; directory records remain 14h. There is no projected STL container or private pool.

`BB7A20` and `BB7BA0` construct into a captured end slot when capacity remains and publish end only after the copy completes. Growth follows the one-element `BB7240`/`BB7640` path: construct an alias-protecting temporary **before** the maximum-count checks `071C71C7h`/`0CCCCCCCh`, choose capacity `max(used+1, old_capacity+floor(old_capacity/2))`, allocate through the canonical `BF55BE` service, copy old records then the temporary, destroy old records and free their backing, and publish the new pointers. Completed new prefixes are destroyed on copy failure through the existing record destructors. Each record copy calls the already reconstructed `BB65A0` or `BB6630`; file offset copies remain delegated to the external `BB6180` library. No whole-record zero or byte copy overwrites padding or allocator preimages.

`A40D60` captures the scalar DWORD before mutation, inserts at the parser's current end, preserves the two-word `{container,pointer}` result and uses the `3FFFFFFFh` element limit and same 1.5 growth rule. It also handles ordinary middle positions with DWORD shifts. The parser only supplies end positions; general alias and invalid-iterator timing in `A40B90` are not claimed as complete. Returning `BF6713` validation is routed to `_invalid_parameter_noinfo`, so callers continue if their installed CRT handler returns.

`BB6220` destroys each completed file record, offset backing first and pooled name second. `BB6E60` and `BB71F0` then free vector backing and clear only the three pointer words; they preserve allocator +0. Directory destruction uses the established `BB6500` source function. The saved listings have **unowned/undecoded** return gaps after `_free` at `BB623D`, `BB6E82` and `BB721A`; each contains raw bytes `83 C4 04` (`ADD ESP,4`). Instructions after each gap belong to the respective root and establish the normal cleanup path. No Ghidra write was made.

The roots' normal parser/teardown paths are source reconstructed. Claimed helper coverage is bounded to the branches reached by those paths. General middle insertion for file/directory records, original length-error object identity, binary callback ABI and in-game reachability remain unproven. `BB6D2B`/`BB6F5B` destroy a completed fill prefix; `BB73EF`/`BB77EE` destroy the fresh prefix and free backing on growth failure. These separately owned catch functions support the source's completed-prefix rollback. The precise nested FH3 rethrow order, partial element failure, and cleanup failure are unresolved; the general-insert catches `BB749A`/`BB7899` are outside parser-reached coverage. `reports/native_mpak_container_storage_az.json` records 76 verified direct CALL rows from saved owners and excludes those separate catches.

The ignored `local/native_mpak_container_storage_az_fixture.cpp` links the built Win32 archive and the **real** worker `NativeMpakOffsetCopyStorage` from `eb6873d0`. It appends five file records with one offset each plus four directory records and checks growth, allocator-word preimages, offset values, and teardown. All 14 allocations made through the borrowed container allocation service are drained; BB6180 and the string/vector helpers use separate CRT allocations.

The ignored `local/native_mpak_container_storage_az_native_compare.cpp` maps verified copied PE code for BB4000..BB7FFF, A3E000..A3FFFF and A40000..A40FFF into isolated executable pages. The original container roots and growth/offset helpers run, with established record copies, BB6180, allocation/free and CRT move supplied by concrete source services. Empty and populated file/directory vector growth, raw BB6220/BB6E60/BB71F0 teardown, and seven offset insertions (including middle growth and middle insertion with spare capacity) match source capacities, values, iterator positions, allocator words and allocation counters. File/directory names are empty in the copied-native comparison, so pooled-name release is covered by the source fixture only. This is a Win32 copied-native fixture, not game execution or general helper EH equivalence.
