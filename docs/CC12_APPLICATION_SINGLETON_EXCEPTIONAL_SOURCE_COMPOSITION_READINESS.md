## Ordinary C++ cleanup and meaningful poststates

Private Source RAII follows the already established render-service/allocation-
statistics pattern. Before guard arming, an ordinary C++ escape invokes genuine
`412430` on the original receiver. After arming, genuine `411EE0` receives the
actual local guard **before** generic-base reset, provided guard cleanup returns.
The Source private helper uses the established second-MSVC-C++-cleanup-exception
termination boundary; other SEH/hardware faults remain outside this contract.
This is not a new Application-owner destructor policy or proof of original FH3.

| Interruption / result | Reached effects and required poststate qualification |
| --- | --- |
| First manager resolution or Enter escapes before guard arming | Base reset only. If it completes, original receiver+0 is `CE3818`; this constructor has not yet published or registered. Preserve the getter's own effects and unknown Enter disposition. No compensating Leave is added. |
| Second manager lookup escapes | Publication of the original receiver was reached; registration was not. Guard then base cleanup may complete, but current publication is not restored or cleared. |
| Registration escapes | Second manager and current-publication argument were selected before entry. Append/validation/provider effects can be partial or indeterminate. Guard then base cleanup does not unregister, roll back, free or resolve escaped storage. |
| Normal Leave escapes as C++ | Normal decrement already ran and registration returned. Guard remains armed, so cleanup can decrement and Leave again. Its counter read is current; no presumed balanced count or safe repeated OS operation follows. Base reset runs only after guard cleanup returns. |
| Guard cleanup itself does not return | Do not claim the `1 -> 0` chain completed or that receiver+0 became `CE3818`. Guard-profile/counter/import prefixes may have occurred. A second escaping MSVC C++ cleanup exception takes the established Source termination boundary. |
| Normal return | Both guards are disarmed; neither cleanup target runs. Return is the original receiver. `D68BC4` is the last **direct** constructor profile store, subject to provider mutations. Current publication may differ, and registration return alone proves neither insertion nor retirement safety. |

If both exceptional cleanups return, the final base reset establishes `CE3818`
on the original receiver. It does not clear publication or remove any registry
entry. A selected null/different registration argument, or a later null current
publication, does not prove the original receiver never escaped. No automatic
retry, counter compensation, extra retain, unregister or free is introduced.
Primitive invalid-access paths and nonreturning providers have no promised
ordinary-C++ cleanup completion. An enclosing retained owner must preserve
their unknown dispositions rather than infer successful construction or cleanup.

The genuine manager getter retains its own lazy allocation/construction/free
policy. That policy concerns its saved manager allocation and must never be
extended to the borrowed Application receiver.
