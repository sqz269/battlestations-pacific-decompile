# CC15 segments 73, 41 (metrics TU) and 61 (telemetry templates)

Packet `cc15-rB1`, worker cc15-rB, 2026-10-18. Part 1 classifies partition segment 73
(`00A62660-00A7A3F0`). Part 2 classifies the `block_metrics_wrapper` rows of segment 41 and the
`block_telemetry_tmpl` rows of segment 61, and reconstructs the game code among them.

Status vocabulary: the C++ in `src/cc15_seg73_41_61.cpp` is **reconstructed and build-tested**
only. It is a new interface over a `Cc15MetricsHost`. It is not ABI-compatible, not fixture-tested,
not wired into the game and not game-validated. Names are hypotheses, not recovered symbols.

### Where Lua ends

The last Lua body is `luaK_patchlist 00A77670`. It ends with `RET 4` at `00A776A0`, so the code
ends at `00A776A3`, followed by INT3 padding up to `00A776B0`. The next body,
`BSP_DialogChannelRecord_SetSpeakerLayout 00A776B0`, is game code.

`tools/progress_board.py` `NON_GAME_RANGES` uses `(0x00a60870, 0x00a7772f)` for the Lua main
block. That upper bound reaches past the Lua code and excludes the six reconstructed game accessors
at `00A776B0-00A77720`. The correct entry is **`(0x00a60870, 0x00a776b0)`**. Lua does not extend
into `00A7772F-00A7A3F0`: that range is all game code (dialog streaming and sound, listed above).
The board file is leased to cc16-progress, so this packet did not edit it.

## Part 2b: segment 41, the MetricsSystem translation unit

The inventory range `00750820-00758000` has both ends wrong:

- `00750820` is the line-of-sight trigger's scalar deleting destructor. It calls
  `BSP_LineOfSightTrigger_DestructBody` and has caller `007501B0`. It is not metrics code.
- The TU runs to `00758090`. `BSP_MetricsSystem_Construct 00757FE0` ends at `00758070`, and
  `CG_scalar_deleting_dtor_00758070` (its deleting wrapper) is part of the TU.

The real TU is **`00750880-00758090`**. It is the game's MetricsSystem singleton (global
`00E1AED4`, 23Ch bytes, built by `cSkeletonAppMidway::Init` at `0073E48A`) and the STL code that
singleton instantiates.

1. Shape-matched each body against every named function (the `tools/template_shapes/st1_shapes.py`
   signatures). The scratch matcher is `local/rb_shapes.py` in the worker tree and is not
   committed.
2. Read the pseudocode of every row and the listing of every game row.
3. Ran a byte census of references from outside the TU.

### Not built

  mission-end score report. It fills the per-category row map and the `+1C4h` flags that

  `play_time`, `ranking`, `End_State`, `Bandwidth_up/down`, `map_usage` and the MissionStart
  rows. It reads gameplay score state but is telemetry, not gameplay. It is renamed (provisional)

- Rows deferred to cc9: **none**. The TU contains no land-vehicle or other gameplay bodies. The one
  gameplay-adjacent row, `00750820`, is a compiler-generated destructor of the LOS trigger and is
  tagged `cg_scalar_deleting_dtor`.

### Reading notes

- Library calls are host methods named by address. ZString is 0Ch bytes and opaque. The
  library's own virtual slots are named by slot: collector `+4` ready, `+0Ch` create metric,
  metric `+8` object `+4` add.
- The trivial logger `004254B0` (a bare RET) is called with format strings. Those calls are
  omitted and the strings are quoted in comments.
- The checked-iterator hooks (`00BF6713`) on the two vector walks test invariants that the walks
  cannot break. They are omitted, and each site says so.
- Upstream callers that already model these calls as host stubs: `frontend_menus.hpp`
  (`metrics_00753810`), `cc13_pkt642.hpp` (`metrics_send_00753570`), `mission_state_frame.hpp`
  (`submit_frame_metrics_00757ce0`), `mission_result.hpp` (`record_metrics_007556a0`), and
  `game_hosts_mission.cpp` (`MissionStart::report_metrics`).
