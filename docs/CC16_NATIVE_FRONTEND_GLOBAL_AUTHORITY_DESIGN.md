## Existing authority and physical image evidence

The existing canonical manager is `game_native_string_process().manager_01090aa0()`. `GameSingletonHost` borrows that exact permanent Source cell in its constructor and exposes it through `manager_publication_01090aa0()`. It is not a fixed-address `01090AA0` mapping. Both new Frame publication and existing `NativeGameSingletonLifetimeContext` must borrow this same manager reference. A second manager cell, even initially null, would split construction and unregister/drain ownership.

`GameNativeCanonicalDataOwner` is the existing intentionally non-destructed process owner. Its success ACK precedes publication of its permanent pointer. `GameNativeReadOnlyData` maps selected original-VA `.rdata` bands; `data_at` admits only `CE2000..E07B23`. `GameNativeMutableCrtData` owns the transferred `E10000` and `01090000` allocation bases but commits only `E15000`, `E16000` and `0109E000`, with narrow CRT accessors. Reserving E10000 is not a committed E18000 page.

## One concrete storage migration, not another global owner

The fixed-VA route is a concrete proposal using the **existing** `GameNativeCanonicalDataOwner`, not an already supplied provider and not a permission to instantiate a dormant bank. It removes the need to relocate original table pointers or maintain a parallel literal table:

1. Extend the existing parent/child capability protocol with a distinct, matched frontend plan/version. Reserve E00000 in addition to the current exact bands; record E08000 and E18000 as explicit frontend writable-page roles alongside the three existing CRT pages. Keep v2 admission unchanged. The current three-page v2 record, `is_canonical_ro_mask`, `plan_mask`, subset-transfer checks and ACK validation cannot truthfully advertise these pages. Simply adding `.data` addresses to `native_data_spans` fails its read-only-section bounds check. A new plan must name the E00000 allocation and distinguish its RO `.rdata` pages from RW E08000. It may select a genuine E00000 RO span and the corresponding extended mask, but that is an explicit new matched plan, not an unexamined widening of v2.
2. Under that same canonical initialization/rollback transaction, commit E08000 RW and copy exactly its authenticated initialized PE page; commit E18000 RW with its genuine zero-fill preimage. Verify the allocation bases, page state/protection, complete preimages and supported PE hash before the ACK. Retain one allocation owner for E00000 and one for E10000; a borrowed frontend subview must never `VirtualFree` either band. The existing RO owner can retain the E00000 allocation while the canonical coordinator admits its separate RW subpage; its `data_at` range remains unchanged. The mutable CRT owner continues owning E10000. Rollback releases each allocation once; success retains them until process exit.
3. Add a mandatory, non-default-constructible borrowed frontend view on the existing canonical owner. It names the actual 95-DWORD base, separate byte sentinel, E18D80 pointer reference, three selector references, three current writable table bases and separate E08654 DWORD. Borrow the existing manager Source reference from `GameSingletonHost`, without mapping/copying it into numeric 01090AA0. The actual Game publication reference must also be the one supplied to `NativeGameConstructionContext::actual_game_00e188a8` and `NativeGameLifetimeContext::game_00e188a8`; `GameNativeGameRuntime` already checks their reference identity. No new parallel Game publication is justified.
4. Publish the view only after canonical readiness and before the first actual Game/screen/Frame constructor or consumer. The Root passes it through the actual application services. This is a once-per-process cold migration, with all corresponding raw producers/consumers switched together. It must not copy an already-live semantic `FrontEndScreenTable`, relocate its two-bool object pointers, reseed tables, zero selectors, or reset any cells when a Frame is destroyed/recreated. If another authority already has live raw publications, migration must resolve that real domain first; nullness alone does not prove a fresh domain.

The view stores references/bases only, no values or default initializers. Suitable roles are `void* volatile&` for publications, `volatile int32_t&` for selectors, `const char* volatile` DWORD table cells on MSVC Win32, `volatile uint32_t&` for flag, and `volatile uint8_t&` for sentinel. Raw bank publication uses actual 32-bit address arithmetic and has no returned-ID range guard. This API design does not claim C++ invalid-pointer/out-of-domain behavior, arbitrary native addressability or the original fault ABI. Mapping the rest of either page authenticates loader bytes, not initialized services at adjacent globals.

An alternative heap array plus hardcoded names would create a second authority without solving Root migration. Adding another `GameNative*Process` singleton would also duplicate an existing process data owner. Neither is proposed. The existing permanent manager Source cell remains the sole manager authority; requiring it to become a numeric mapping is unnecessary and would disrupt every existing manager borrower.

## Raw receivers and current dispatch

At baseline `GameMenuHost::Impl::world.screens` owns `FrontEndScreenTable` (95 semantic pointers and an embedded sentinel); each `FrontEndScreen` contains only two bools. `Impl::frame_layouts` separately owns typed `FrontEndFrameLayouts`. `MenuFrameLayoutHost` returns semantic `GuiLayoutPage` objects, substitutes hide-for-destruction and chooses pause-page visibility. These are the current gameplay projection owners, not raw Frame storage or actual Page ownership. Replacing only the bank parameter would publish invalid raw receivers into a consumer graph that still expects the semantic layout.

The admitted raw getter returns BF681B-allocated 164h storage. Its constructors write profile identities and bytes+4/+5 only; +C..160 are untouched. Actual CEC39C has +00=517D30, +0C=517EB0, +10=517ED0, +24=518E00; CEC398 at receiver+8 has +00=517D50, which performs receiver-=8 then tails 517EB0. CEC388's +00=517D60 is a different constructor/base lifetime profile. CEAE54's ID slot is purecall, not a usable default ID.

A concrete retained per-receiver dispatch/lifetime facility is required at Root. It must recognize an actually produced live receiver, read its CURRENT profile, capture that table's CURRENT requested codeword, then invoke the corresponding genuine Source operation. CEC39C/517D30 resolves to the existing actual constant-return body, not a metadata `ReturnInt`, semantic label, supplied id or guessed12. Profile/code DWORDs are never cast to host callable pointers. A finite Source resolver may admit only established real profiles/targets and must expose unresolved ones as an unclosed provider boundary; an unknown-target success fallback is not permitted. Ownership metadata must preserve older live receiver identities across publication replacement, rather than require `receiver==CURRENT E18D80`.

Whole raw base registration4F71D0 captures its receiver, calls CURRENT profile/+0 with that receiver and publishes the captured pointer at `E18B60+4*returnedEAX`, unchecked. Its authentic return id remains returned on the normal native path. A callback can alter publication/profile; this does not change the captured receiver to publish. The existing `register_front_end_screen_004f71d0(table,twoBool,id)` and `register_main_menu_screen_00582f30`'s id/range guard are qualified projections; neither is this raw operation. Raw base destruction4F71A0 must first stamp CEAE54 then scan all95 cells and clear every exact receiver match. Clearing just ID12 or only the current publication would change native behavior.

The needed receiver provenance includes each actually reached screen creator, its real prefix/size/fields and current slot bodies. In particular, the current press-start, main-menu, HUD42 and other semantic screens cannot be cast or copied into raw objects. An array of 95 nulls with only the Frame populated would leave their registration, recompute, pump and park consumers unsupplied. This is why the data/view change alone is not a coherent current caller-adoption packet.

## Value epochs that the view cannot flatten

Registration517ED0 first executes real base registration, then writes own+160=4 and all85 Page words. It captures each outer name from CURRENT own+160-indexed writable tables and rereads own+160 for inner-row decisions. Real pool/getter/Page callbacks separate those reads; authentic initial row4 happens to load no Page. This initial phase does not justify refusing later table mutations or omitting nonempty producers.

Set518250 compares the real requested home with current own index; initial commit-byte read governs retirement. Each retirement-row skip rereads requested home. Count==1 takes CURRENT GUI getter then reloads Page for AA31F0; otherwise it captures current Page, decrements that object's +4 through the genuine retained CE2220 import and dispatches captured Page's CURRENT slot0 at zero. Only returned retirement clears the actual slot, including callback replacement. Each acquisition group separately rereads requested home; each slot reads CURRENT name even when already present. Final commit byte and requested home are reread after acquisition before own+160 publication. A value `int set,bool commit` wrapper, table snapshot, clear-before-call or forced-row4 provider cannot preserve these epochs.

Writer518D60 captures the title argument DWORD first; writes84,88,8C; calls getter/apply; only then reads the CURRENT stacked text-pointer home and CURRENT header length for title. Writer518DA0 writes84 then getter/tail apply. Apply518C80 keeps its captured real receiver while reloading own+160, selector cells, Page receiver and current+34 targets at their native phases; actual Game+5D4 mode0D skips backdrop and flag tail. Flag518B90 stores E08654 DWORD and uses its later low WORD at the widget call. Title/position routines consume selectors through their own repeated getter/receiver/index schedule. The existing typed `FrontEndFrameSelection` four-field object cannot overlay these discontiguous cells.

Collector518E00 loads own+160 separately at518E03,518E2A,518E4B, with the respective selector reads at0C/30/51. It captures each slot ADDRESS before4D6790; this append may change the receiver's fields or global publication before the next group. The legacy Source collector caches `own` and computes all three offsets up front, so binding its host alone does not repair the schedule. Whole raw body/current-call review is required without duplicate reconstruction credit.

Global selectors/names/flag survive old/new Frame generations. Frame+160 and its85 Page words belong to each receiver independently. The current publication can change while a captured old receiver is still used; no receiver==publication restriction, selector reset, automatic table restoration or per-Frame selector copy is native behavior.

## Unpublication, replacement and drain

Retain the exact allocated Frame identity, +8 singleton subobject and all operation/provider contexts. Primary scalar517EB0 calls full517D90, then reads the actual low flags byte from its current argument home and conditionally frees captured storage when `flags&1`. Secondary517D50 adjusts-8 before that route. Destruction stamps the real Frame profiles, traverses all85 slots slot-major/set-minor and calls actual current GUI/Page retirement for every nonnull slot, then clears E18D80, stamps secondary CE3818 and runs raw4F71A0's full95 scan/profile store. Do not infer readiness from an empty initial register; later title/pause pages require their actual lifetimes.

Clear helper517CF0 and scalar517D60 also write the SAME E18D80 cell. These native writes clear it unconditionally; they are not compare-and-clear-if-this. Likewise4C0CE0 captures manager section, captures adjusted publication before its second manager lookup, unregisters it, reloads CURRENT publication for primary scalar+0C(flags1), then clears the publication AFTER returned scalar. A callback-created replacement can therefore be cleared by later native writes. No rollback, generation-equality guard, extra retain or automatic replay may be added to hide those effects. Failure must retain partial publications, graph and operation diagnostics for actual resolution.

Current `GameStartupHost` teardown deletes `menu_` and `frontend_` **before** `drain_native_singletons()` (`game_hosts.cpp:2312..2336`). Native Page/GUI manager bindings are already retained until after that drain. The proposed raw Frame service graph must move out of `GameMenuHost::Impl` into the existing Startup-retained service lifetime, or Root must reorder its genuine lifetime so those same services remain alive through Game OnDestroy and normal/fallback manager drain. Borrowing `MenuFrameLayoutHost` across the existing order would leave dangling callbacks. Retain VFS/Lua/renderer/string/scene/child/timed ownership needed by actual Pages, release Frame while these providers live, complete shared manager drain, then retire borrowed bindings. Canonical global pages and manager publication cell outlive all these object epochs and later CRT callbacks.

## Implementation boundary and exact outstanding providers

The storage/view proposal has a small identifiable file surface: existing native-data bootstrap header/CPP and `game_main` plan selection; existing canonical-data owner header/CPP plus a borrowed view definition; Startup/Singleton/Menu binding sites listed above. It is a data migration with no new Original function credit. It is only coherent with the following concrete closures; implementing it as an unused zero bank is not the next admitted packet:

* A genuine raw95 creator/current-ID and other reached slot-dispatch domain, with actual receiver sizes/flags/lifetimes; raw base register and destructor semantics; complete consumers of the same bank/sentinel. The admitted ID12 body supplies one real target, not the other receivers or whole registry. Main-menu/press-start/HUD semantic storage remains an actual migration prerequisite.
* Whole517ED0 and518250 providers using the proposed current cells and real NativeString/pool/memcpy/GUI getter services, request/commit homes and cleanup epochs. Existing real CE2220 is retained by the actual Page layer/camera-scene domain; do not invent a missing OS body/accessor. Full apply/flag/title/position/current-dispatch services and title x87/math/ambient-environment qualifications remain required.
* Actual `GameNativeGuiPageApplication::Impl::Page` production and retirement of the SAME nonempty Page/Group/Model/child/node/timed graph. Its mapped-key miss currently rejects BEFORE AA6560/Model creation; its private lifetime provider rejects child/timed/parent routes and requires prior scene release. Existing complete AA38F0/AC5480/AA9730/AA8320/AA31F0/BD30E0 bodies, Group/ClipBox/Text/Icon dispatch and separate FrameBox identity contexts must be composed with real reached AA6560 creators and authored layout/type preimages. Removing guards, childless hits or semantic pages do not supply this graph. Count-zero/current0 ->BD30E0/current04 remains distinct from manager AA31F0 ->current20/fresh04.
* Actual Frame scalar/destructor/adjusted lifetime binding on both Game4C0CE0 and shared manager drain, including partial getter registration failure. All creator/register/selector/captured-collector/park/hint/pause/Game callsites must use the same authority and keep services alive across existing teardown boundaries. `InitOnceServices` and complete native Game construction/lifetime contexts remain required application bindings; their abstract existence is not Root adoption.

This permits bounded follow-up work on the existing real Page producer/lifetime composition and individual actual screen/slot contracts without a whole-GUI rewrite. It does not identify a closed standalone new global-owner implementation today. Once those providers exist, one Root migration batch can implement the explicit capability/view and the listed ownership/callsite changes, validate exact reference identities and ordered replacement epochs, build MSVC Win32 with existing checks, and then satisfy the required fixture/startup/gameplay gates. No gate is bypassed or reclassified by this design.
