# Native read-only data handoff at `bsp_game` entry

`src/game_main.cpp` now uses the controlled `GameNativeDataBootstrapChild` path for every normal `bsp_game.exe` launch. The parent parses the public options, resolves `battlestationspacific.exe` from the selected `--game-root` or its current directory, checks its size and SHA-256, and creates a **new suspended copy of its own executable**. The bootstrap reserves the four 64-KB bands at `00CF0000`, `00D10000`, `00D50000`, and `00D60000` in that child, then resumes it. It refuses an occupied band; entry neither releases foreign memory nor starts the original game executable.

The bootstrap alone appends `--bsp-native-data-handoff=<inherited handle>`. Entry recognizes a final token with the exact eight-hex-digit form and an inherited handle, removes it before `GameExecutableOptions::parse`, and otherwise preserves the public argument vector. Forwarding uses `CommandLineToArgvW` and Windows backslash/quote escaping, including empty values and paths ending in backslashes. The child accepts the one-use handoff, verifies the complete original PE SHA-256 through `GameNativeReadOnlyData`, and maps its read-only table/literal bands before constructing `GameStartupHost`. The mapper outlives the host and its destructor. The parent waits for the mapping acknowledgement, then waits for the child process and returns its actual exit status. The bootstrap terminates only its own child when startup is incomplete.

The child attaches to its parent process's console because the bootstrap restricts inherited handles to the mapping handle. Only the child opens `--log`; it does so before `--game-root` changes the current directory, retaining the previous relative-log behavior. Public settings, screenshot, trajectory, and DLL paths are resolved by the existing option parser before that directory change. Native-data and bootstrap failures are printed to stderr, and child-side mapping failures are also recorded in the selected log when it opens.

The supported original image in `config/target.json` is 12,223,752 bytes with SHA-256 `B682A82C52F81F957B2C70222077305A933F72481686C88843077F714B956DD6`, matching `GameNativeReadOnlyData`'s pinned identity. The parent repeats this check to report wrong images before launching a child; the child independently verifies the bytes before mapping. At the pre-integration snapshot, the built `bsp_game.exe` had preferred base `00400000`, `SizeOfImage=001F6000`, end `005F6000`, and `DYNAMICBASE` enabled. The preferred image does not overlap the first requested band, but ASLR could place a child image there. The integrator owns any linker placement change; the reservation still rejects collisions.

This packet's verification is strict x86 MSVC compilation of `src/game_main.cpp` with `/std:c++17 /EHsc /W4 /WX /fp:strict` and an entry/protocol source review. The parent integration owns the full link and raw host admission. No game runtime or visual validation is claimed here.
