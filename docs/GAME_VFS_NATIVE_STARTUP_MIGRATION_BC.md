## Current lifecycle and consumers

Source `GameStartupHost::~GameStartupHost` (`src/game_hosts.cpp:1014-1052`) drains `singletons_` before destroying script/settings/front-end/VFS owners. `application_shutdown` (`:1642-1646`) still records singleton teardown as unimplemented; it is not evidence that the raw VFS has been drained by that callback.

## Raw graph already available

`NativeVfsManagerLifetimeContext` (`include/bsp/native_vfs_manager_lifetime.hpp:33-45`) borrows actual `0109CEEC`, `0109CEE8`, the shared lifetime manager, pooled strings, canonicalizer, six literal examples, validation and virtual dispatch. `construct_native_vfs_derived_manager_00beda60` adds the actual physical factory to the base manager's raw list (`native_vfs_derived_manager.hpp:8-24`). `register_native_vfs_provider_factory_00be0660` appends raw nodes (`native_vfs_factory_registration.hpp:17-36`). `NativeVfsMountRegistrationContext` and `mount_native_vfs_system_path_00be1890` (`native_vfs_mount_registration.hpp:21-53`) use actual string headers and the current failure callback. Lookup/open/exists routes are in `native_vfs_lookup_routes.hpp`, `native_vfs_open_route.hpp` and `native_vfs_runtime_bindings.hpp`. MPKG/MPAK, FileStore, physical and memory modules contain substantial concrete provider/stream operations; `NativeMpakLookupStorage` now implements the formerly absent BB4140/BB4F40 lookup leaves, and `NativeMpakOffsetCopyStorage` supplies the offset-vector copy interface. This changes the older AZ audit's missing-MPAK assessment, but does not establish full factory/mount/read composition.

The BB `NativeVfsOwnerServices` bundles stable borrowed cells for `01090AA0`, `0109CEEC`, `0109DC28`, `0108FE8C`, `0109DBBC`, `01090AA8`, `01090AA4`, `0109DB7C`, and retains raw string, physical-date, batch, stream and type-counter services with one `SoundLifetimeAccess`. Its contract explicitly does **not** construct a manager/provider or run shutdown. The host must additionally retain `0109CEE8` log, physical provider pool `0109DBF0`, FileStore/MPKG/MPAK factory and registry publications (`0109DB68`, `010904D8/E0/DC`), native path and library services, provider dispatch contexts, raw string payloads, and readable original numeric table data. Each publication and context must remain stable through raw manager drain; the original numeric table words must resolve to mapped readable data before first virtual-slot read. A numeric owner identity alone is insufficient.

## Contract gaps that block a single-step host replacement

1. **Factory and mount composition.** The current four token getters and projected list have no raw owner identity. A game-side composer must retain actual FileStore/MPKG/MPAK factory singleton storage and attach them in native call order after the physical factory constructor append. It must call `mount_native_vfs_system_path_00be1890` with actual pooled headers, canonicalizer and source dispatch (`native_vfs_mount_registration.hpp:21-53`). Existing concrete `NativeVfsRuntimeBindings` implements factory-create dispatch and `NativeVfsStartupCallbacks` (`native_vfs_startup_callbacks.hpp:22-26`) implements the verified manager+90 startup no-op target, with `install_native_vfs_startup_callbacks_0073d63c` preserving publication reloads. The host supplies neither retained binding nor original table image yet. Other captured callback targets remain an explicit boundary.
2. **Package/search behavior.** `GameVfsHost::package_scan_callbacks` at `game_hosts_vfs.cpp:180-211` enumerates projected `VfsMountContext` resources and remounts through its projected manager. Its two-pass result and `VfsCandidateRegistrations` are source-side projections. A raw path needs native enumeration/lookup and the correct current mounted-provider skip; retaining the old callbacks against a second projected context would split state. Search registration and alias writes likewise need actual raw manager storage before the current `resolve_existing_resource_00bdf4c0_fragment` consumers can be retired.
3. **Read/exists conversion.** `NativeVfsRuntimeBindings` (`native_vfs_runtime_bindings.hpp:28-84`) can dispatch supported numeric manager/provider/stream profiles, but borrows open, lookup, physical, FileStore conversion, logging, retained-memory and provider contexts. `native_vfs_open_route.hpp:12-63` states BDF310 still requires BDE9C0 logging and callable provider/stream/failure services. `NativeMpakRuntime` supplies a concrete captured provider+24 resolve dispatch for its supported profile (`native_mpak_runtime.hpp:41-56`); a general device route still needs each reached provider profile proven. The binding's numeric memory/physical `source_write` path is unsupported. A production read adapter must define raw string ownership, stream read/size/release and failure propagation for every current consumer; returning a projected `MemoryStream` or silently reporting success is not that contract.
4. **Shutdown.** Raw manager publication and all registered owner cells must survive the single actual `01090AA0` drain. Bind deletion before any getter registers, then release raw VFS contexts/table data only after drain. Preserve `GameStartupHost`'s current consumer-before-VFS destruction order, and do not let `GameVfsHost`'s `unique_ptr` destruct a raw owner separately. Exceptional startup needs the same retained cells and cleanup path.

The smallest **first production packet** is a new disjoint game-side retained `GameNativeVfsRuntime` composition API in new header/source plus `cmake/startup.cmake`: borrow BB `NativeVfsOwnerServices` and the host's one raw singleton manager; own all VFS-specific publication cells, numeric table-data mapping, canonicalizer, factory/provider/lookup/open/logging contexts; construct a raw A0h manager and expose explicit raw read/exists and phase-2 mount operations with owned string/stream boundaries. Its acceptance requires a focused raw manager + all-four-factory + three-mount + MPKG/MPAK lookup/open exercise and drain on one shared manager, including failure/unwind. Only after that should a separate game-host migration change `game_hosts_vfs.{hpp,cpp}`, `game_hosts.cpp`, and the eight `manager()` consumer source files together, preserving phase order and adjusting shutdown. Phase-6 parser state is a separate resource-manager dependency; raw VFS composition does not justify casting that projected manager either.

No native function addresses or Ghidra names are claimed by this source audit. Existing source headers provide the native-address labels above; direct CALL attribution would require a separate verified listing receipt. No game, original executable, archive or host startup was run.
