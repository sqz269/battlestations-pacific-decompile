## Three-file and two-file choices

For the requested exact escaped-edge check, prefer the finite three-file design: Glyph HPP/CPP plus ONLY an exact existing-entry friend declaration in Origin HPP. Existing forwards suffice. No protocol CPP/API change, new public service, Cause friendship or generic accessor is needed. The exact declaration is recorded in the report. The actual entry may read Origin's private escaped fields; actual current-cause equality stays delegated to existing HeaderArm.consume, since Origin friendship does NOT grant access to Cause::same.

Capability limit: C++ friendship grants FULL Origin private access to this function and its lexical lambdas, not language-enforced read-only access. The declaration alone executes nothing and adds no issuer/proven_native writer. Acceptance must inspect the actual guard body and reject any new private-field write, synthetic cause/edge, issuer assignment, proven_native commit, escape of a privileged closure, public Native flag or unused service. A const Origin view for the guard reduces mistakes but does not remove the language capability. Existing public negative methods may still do their established work; the new private guard reads only.

The two-Glyph-file variant is acceptable ONLY as explicit denial-only safety. Top retain_current can commit sticky Unknown and the issuer-free arm cannot authorize cleanup, but this does not authenticate the exact failed edge or child Host receipt. Do not advertise the stronger predicate or future Native safety for that variant. Any later issuer/child promotion requires a fresh audit. A two-file variant must not smuggle a new public phase/diagnostic-based Native authority to avoid the friend decision.
