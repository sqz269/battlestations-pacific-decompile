# GUI owner composition at WM_ACTIVATE (CC10 audit)

This is a source and native-call audit, not an application binding or game validation. The branch audited is `agent/cc10-platform-activate` at `a4f03c841`. The native getter can run from the window procedure before the frontend exists. The current frontend later creates a different semantic manager and typed pages. Consequently a focus callback aimed at the raw getter would see an empty raw page vector, and creating that getter's owner currently leaves the singleton drain without a deletion arm.

## Lifetime contract and missing work

`004C12B0` registers the raw owner with the singleton manager. The current `NativeSingletonDeletionBindings` (`include/bsp/native_singleton_destruction.hpp:73-~155`) and `src/native_singleton_destruction.cpp` have no `00D5BFCC` dispatch; `:477` throws for an unrecognized profile. The available `destroy_native_gui_manager_00aa6340_fragment` (`src/native_gui_media_focus_lifetime.cpp:118-150`) needs real current-page virtual +20 and +04 providers. The native loop calls +20, reloads the page pointer, calls +04 with flag 1, then releases +28, string list +34, +2C, vector and tree, and clears the publication. `NativeGuiPageLifetimeHost` has two separate mandatory methods (`include/bsp/native_gui_media_focus_lifetime.hpp:8-29`). `GuiWidgetOwnerRuntime::retire_tree` has a related scene-release order (`src/gui_widget_owner.cpp:740-760`), but is not a raw page virtual dispatcher.

The movie dependency is also concrete: `GuiTypeDispatchFactory` has no `GuiWidgetType::Movie` case (`src/gui_type_dispatch.cpp:259-295`), while `MovieWidgetState` is explicitly a projection, not a native cGuiMovie (`include/bsp/movie_player.hpp:38-~105`). The existing `NativeWindowFocusContext` can validate actual vtable targets and call the shipped Bink pause import (`include/bsp/native_window_focus_dispatch.hpp:11-49`); it cannot create the decoder or raw widget/list fields needed to reach it. Any typed traversal must reject an unsupported Movie widget rather than silently return success.

Current `GameStartupHost::application_shutdown` in `src/game_hosts.cpp:1955-2049` deletes menu then frontend, releases device, and leaves full native singleton teardown unbound. `GameStartupHost::~GameStartupHost` at `:1250-1310` likewise deletes frontend before singleton drain. Native GUI pages that borrow layout, scene, decoder or texture services would therefore outlive them if simply admitted to the raw manager. `release_screen_page` (`src/game_hosts_frontend.cpp:1032-1040`) only erases a screen set entry; it does not implement native page reference release `00AA31F0`. `GuiResourceOwner` (`include/bsp/gui_resources.hpp:31-~107`) offers a stronger typed resource-state contract but still borrows `GuiPageRegistry` pages, so it cannot serve as the raw 0x88 manager unchanged.

Smallest truthful migration, in dependency order:

1. Put **one** GUI composition in `GameStartupHost`, alive before window creation and through singleton drain. It owns stable actual publication cells, raw getter context, raw manager pointer through the singleton manager, and the required lifetime/service bindings. Window focus and frontend startup both request `004C12B0` through it; do not create a second `ManagerState` or independent GUI publication. Bind `00D5BFCC` scalar deletion before the getter can register a singleton, including the empty early-owner case.
2. Change `GameFrontendHost` to borrow that composition. Treat its typed registry, script tables, resource log and sprite bridge as **views/companions** of admitted native page identities. Replace `store_gui_resource`'s `ManagerState*` cast with offset-specific publication of actual raw resources into the one manager; preserve each slot's reference/release contract. Resource creation must return or map to the actual page/widget/texture identity expected by that slot. Keep diagnostic typed pages separate until the corresponding native page has actually been constructed; never insert a typed pointer into raw storage.
3. For each production page, construct the actual 0x124 page/profile and required raw child/list/node associations, using existing scene/widget components only where their same-owner identities and current virtual targets are proven. Register it once in the raw +14 vector through `00AA52A0` behavior; make semantic lookup point to that page's companion. `00AA33A0` may then traverse it. Unsupported movie decoder or page virtual behavior must remain an explicit failure/dependency, not an empty callback, fake pop, or claim of successful pause.
4. Reverse the present shutdown dependency: menu/screen references retire first; the raw GUI singleton drains while typed layouts, scene/widget runtime, movie/renderer/string services and device remain alive; only then destroy typed frontend companions and underlying services. Have the singleton manager perform the one scalar delete; do not manually delete and later drain the same registered pointer. Handle exceptional startup with the same order and publication identity.

The narrow first integration can share an *empty* raw owner between early focus and GUI startup once deletion is bound, while leaving typed pages diagnostic and reporting that activation movie propagation does not yet reach loaded pages. Claiming the requested full production ownership requires steps 2-4, including a genuine raw page producer. No source or runtime changes were made in this audit.

An integration packet can therefore be split by producer dependency: **A** owns `native_singleton_destruction.hpp/.cpp`, `game_hosts.hpp/.cpp`, `game_hosts_frontend.hpp/.cpp` and a new durable composition interface, and establishes the single raw getter/deletion identity plus typed sidecar while explicitly limiting activation to the empty raw vector. **B** owns the frontend loader and GUI native-scene/page-runtime files, constructs and registers actual raw pages, maps typed companions to those identities, and implements both page virtual providers and resource slots. **C** supplies the Movie type/decoder identity needed for populated movie focus, or keeps that profile an explicit admission failure. These are dependency-ordered packets, not independently releasable claims of full WM_ACTIVATE parity.

## Correction from docs/GUI_MEDIA_SINGLETON_DISPATCH_CC10.md

The later CC10 integration adds both `00D5BFCC` GUI and `00D24D94` media singleton deletion arms with separately required lifetime bindings. A populated source-page probe passes through the shared manager drain, including changed publication and page-pointer reload. The missing deletion arm identified above is therefore closed at the dispatcher level. Production owner creation, frontend/page identity and teardown composition remain unbound; this does not close the other admission requirements in the audit.
