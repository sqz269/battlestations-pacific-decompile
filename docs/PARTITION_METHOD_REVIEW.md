# Frozen partition method review

The frozen 23,992-candidate / 87-segment report is useful for assigning function-entry ownership and locating related code. Its ranges and waves do **not** establish independent reconstruction tasks. Dependency loss in scheduling is a concrete implementation issue; incomplete graph coverage, name-based exclusions and semantic labels are additional evidence limits.

This review concerns the proposal captured in `local/partition_review/input/`, frozen at `2026-09-09T20:32:47.262036+00:00`. All 11 input hashes matched its `manifest.json`. Paths and line numbers below are relative to that frozen directory, **not current working-tree versions**. The report was regenerated by the discovery pass during initial inspection: an earlier 96-segment view became the 87-segment baseline reviewed here. Stable task addresses matter more than these changing segment IDs.

The corrections have since been applied and independently checked against the same inputs. Full outgoing/incoming maps are retained in JSON, scheduling uses all qualifying edges, Markdown shows SCC IDs/sizes, purity uses the largest original community, and labels state the heuristic scope. Input, executable, generator and snapshot hashes/identity plus NetworkX version now accompany the report; the sweep records function-list identity and Capstone version. The final pointer run is flushed. Cross-segment table identities and complete indirect-call/shared-state coupling remain unverified.

The real-data check restored 458 qualifying edges (7,309 unique caller-target relationships), enlarged the largest SCC from 46 to 84 segments, and changed 38 waves. All 87 ranges and 23,992 candidate identities/counts stayed unchanged; eight purity fields changed. See [partition_validation.json](../reports/library_inventory/partition_validation.json) for retained input hashes and metrics, and [PARALLEL_WORK.md](PARALLEL_WORK.md) for actual work assignments. The findings below explain the frozen proposal and remaining limitations; they do not imply that the corrected scheduler still drops edges.

## Scheduling

- **Dependencies are truncated before scheduling.** `tools/partition_candidates.py:166-176` keeps six destinations for display, then builds the dependency graph from those six. Segment 2 loses eight destinations meeting the threshold, including segment 85 with 11 unique caller-target relationships. Segment 53 loses 31 qualifying destinations, including segment 41 with 53 relationships. Build the dependency graph from the complete segment counters; truncate only presentation. This can change SCC membership and waves, not merely hide report detail.
- **Same wave is not an independence declaration.** Condensation followed by topological generations of the reversed graph is the correct leaf-first ordering for caller-to-callee edges (`:170-185`). Different SCCs in one generation have no retained dependency edge between them, but members of one SCC are mutually dependent and deliberately share a wave. The frozen JSON includes 46 segments with `cycle_group_size:46`, yet emits no SCC identifier or membership list; the Markdown omits even the size. Emit both SCC ID and members. A wave-0 SCC has no retained outbound dependency on *another SCC*; its members may depend on one another.
- **The weight is a relationship count, not call-site frequency or runtime strength.** The sweep stores targets in sets (`tools/callgraph_sweep.py:49,59-66,74-75`). Repeated calls from one function to one destination count once, and direct tail jumps count too. Partitioning adds one per retained caller-target pair and combines reciprocal edges for undirected clustering (`tools/partition_candidates.py:86-97`). This is a reasonable structural heuristic if labeled accurately. A threshold of eight relationships is a scheduling preference, not evidence that seven relationships are safe to ignore; one relationship can carry a critical ABI or ownership contract.
- **Static direct edges omit important coupling.** The sweep decodes from each exported start to the next start (`tools/callgraph_sweep.py:46-57`), rather than recovering reachable instruction blocks or using native function bodies. It records only direct calls/jumps into `.text`; the partition then requires exact candidate entry-point destinations (`tools/partition_candidates.py:89-92`). Indirect dispatch, callbacks, shared mutable globals, interior targets and dependencies through excluded named functions are absent. Possible code/data or missed-body errors are not quantified here. Treat no edge as “not observed by this sweep,” not proof of independence.

## Candidate and boundary meaning

- **The queue is unnamed non-thunk functions, not all unfinished work.** Eligibility is solely `name.startswith('FUN_') and not isThunk` (`tools/partition_candidates.py:71-77`). No reconstruction status or tag policy is consulted. All 54 distinct addresses represented by the frozen reconstruction ledger's 63 fragment records are excluded. For example, `00b2aeb0` is named `BSP_D3D9Renderer_InitializeDeviceAndResources` (`exports/bsp/functions.json:177621-177624`), but its ledger explicitly leaves substantial work unported (`config/reconstruction.json:1230-1236`). Keep a separate named-but-incomplete queue; do not interpret naming as completion or a callable replacement boundary.
- **“Untagged” is inaccurate, but blanket tag exclusion would also be wrong.** There are 1,554 candidate addresses in the tag ledger. All are medium-confidence `stl_probable` bookmarks, not confirmed rename classifications. The evidence at `config/ghidra_tags.json:463-470` explicitly says “bookmark only.” Call these unnamed candidates and retain their triage tags. Review tentative library matches before excluding or reconstructing them.
- **Address ownership is sound when defined by the explicit candidate set.** An independent recomputation using NetworkX 3.6.1, the frozen parameters and seed reproduced all 87 reported ranges. Each contiguous slice receives one segment (`tools/partition_candidates.py:123-126`). The printed endpoints are first/last candidate *entry points*, not native function-body boundaries (`:163-164`). Segment 86 spans 1,817 exported function starts but contains only 536 candidates; its other 1,281 functions need an explicit access/ownership policy. Assign exact addresses and source files, not an ambiguous blanket claim over every byte in a printed range.
- **Link-order locality is a hypothesis, not recovered module identity.** The opening assertion that one source module occupies one contiguous `.text` range (`tools/partition_candidates.py:3-8`) is not validated by object/PDB/link-map evidence in these inputs. Louvain intentionally removes call direction, smoothing uses candidate-index distance rather than byte distance, and short segments merge leftward rather than toward the best-connected neighbor (`:86-122`). These choices produce useful contiguous work ranges, but do not recover original translation units or class boundaries. Record parameter/version provenance and inspect boundary functions, shared types and ownership before dispatch.
- **“Purity” is not always largest-community share.** After merging, the retained label need not be the modal original label (`tools/partition_candidates.py:117-120,156`). Eight frozen segments exhibit this. Segment 4 reports approximately 0.08 for the retained label while its largest community occupies 0.206; segment 22 reports approximately 0.12 versus 0.250. Either rename this measure to retained-label share or recompute the mode after final merging. Even a true community share measures agreement with clustering, not semantic confidence or independence.

## Labels and evidence limits

- **“Vtables” are candidate function-pointer runs.** The scanner counts aligned `.rdata` runs of at least three pointers to exported function starts, with no RTTI, constructor store, dispatch or table-boundary validation (`tools/partition_candidates.py:128-142`). Adjacent tables can coalesce; short tables can be missed; the final run is never flushed at section end. A run spanning segments is credited to only its plurality segment, concealing cross-segment sharing. Rename the measure, preserve run addresses/slots and cross-segment membership, flush the final run, and validate important candidates against native evidence before treating them as class contracts. The reported 847 count is not a verified class/vtable count.
- **Keywords are narrow clues.** Only NUL-terminated printable ASCII strings of length at least five in `.rdata`/`.data` are scanned (`tools/partition_candidates.py:30-43`), and only exact-address references captured by selected instruction patterns contribute (`tools/callgraph_sweep.py:67-71`; partitioner `:80-84`). UTF-16, indirect string tables and some substring references are omitted. Keyword scoring suppresses common tokens, but does not establish subsystem identity (`:149-155`). `lua_bindings` counts candidate functions containing a `luaMW_` token in directly referenced strings, not recovered registration records (`:46-55,150-152`). Use “Lua-marked functions” until registrations are checked.
- **Reproducibility needs input identity.** The partitioner reads a fixed default config/functions path but independently configurable graph/data-reference paths, and does not validate input identity (`tools/partition_candidates.py:61-78`). Output records algorithm parameters, but not input hashes or package versions (`:188-190`). The sweep records the executable hash but no function-list hash (`tools/callgraph_sweep.py:80-85`). Record and validate snapshot/program/binary/function-list identities across the batch; support the project's local config override convention.

No Ghidra database, executable, C++ or shared metadata was changed for this review. The frozen manifest and range reproduction were checked; native class identities, complete call-graph accuracy, ABI contracts, compilation and gameplay behavior were not verified. Parallel work can proceed as bounded evidence investigation with disjoint function/file ownership, explicit shared-type owners and coordinated metadata integration. Reconstruction readiness requires those contracts in addition to the corrected graph.
