# CC15 g24b: game rows from the stl_probable audit

Packet cc15-g24b. The cc15-stlA audit (docs/CC15_STL_PROBABLE_AUDIT.md) moved
these rows from stl_probable to game_code. Each now has a body in
`src/cc15_g24b.cpp` (interface `include/bsp/cc15_g24b.hpp`, namespace
`bsp::cc15_g24b`). Names are hypotheses, not recovered symbols.

Status: reconstructed, build-tested. They are new C++ interfaces, not ABI
drop-ins, and none has been checked against the game. No host calls them yet.
Each body's signature matches the existing host seam for the same address,
so a host could implement that virtual by calling the body.

Every field access goes through `MemoryHost::read_u32/write_u32` on native
Win32 addresses, and every call goes through a host virtual. The VC9 checked
iterator asserts call 00BF6713 and fall through in this image. Each one is a
host call at the same place, and execution continues the way the binary does.

## Evidence

- **004881F0.** The saved listing (004881F0-00488284) walks the std::list at
  `[manager+8]+0Ch`. The head is at +10h, a node keeps next at +0 and the
  object at +8. The iterator's container (EDI) is read once. The end() side
  re-reads `[manager+8]` on every pass. An object whose word +4 is 2 (tested
  first) or 1 gets `CALL [[obj]]` with 1, the scalar deleting destructor, if
  the object is non-null. Its node is not unlinked.
- **0048CA60, 0048CB30 and 0048CBB0** run under the manager lock.
  EnterCriticalSection `[manager+4]` goes through `[00CE2218]`, followed by
  `++[cs+18h]`. At the end, +4 is re-read, `--[cs+18h]`, and
  LeaveCriticalSection goes through `[00CE2210]`. Inside the lock each one calls
  00488630 `STL_Tree_Find_00488630` (ECX = manager+28h, out iterator, &key)
  and reads `[tree+4]` after it returns. The found node's +10h is the entry.
  - 0048CA60 builds the key as `([record] ?: [record+8]) + 1E4h`, or 0 when
    both are zero, and stores it over its argument slot. It then increments
    `[[entry]+D8h]+10h` when the low byte of flag is set, else +14h.
  - 0048CB30 sets `[entry+DCh] = 0`.
  - 0048CBB0 starts with result byte 0. It returns 1 when the entry is found
    and both `+DCh` and `+BCh` are non-zero. Its second dereference check
    (0048CC1B) has no null-container test.
- **00687860.** The flag is tested first: with the low byte 0 and
  `[this+20h] == id`, it returns 1. Otherwise it scans the dword vector at
  +5Ch/+60h. The size is `(end-begin) SAR 2`, compared unsigned. The range
  assert reuses the begin register and re-reads end, and the element read
  re-reads begin.
- **006A9EA0.** 0055C110 (`operator[]`, which inserts when the key is absent)
  on settings+8 returns the value. The value's tree is at +0Ch (head +10h) and
  the iterator container is cached in the argument slot. For each node it
  checks elements 0 and 1 of the 14h-byte vector at node+18h/+1Ch: assert if
  begin is null or the index is not below `span/14h` (signed IMUL 66666667h
  divide, unsigned compare), then return 1 if the element's first word is 2.
  It advances with 00552DB0.
- **006AA1C0 and 006AA2D0** are the same body: same map walk, same callees,
  same offsets. Both walk the map at +8h (head +0Ch) and call 0055C110 on the
  map at +6Ch with the node key (node+0Ch). Each then does three tree
  assignments, skipped when destination equals source: 005599C0/0055A160 for
  value+0Ch and node+20h, 00444B10/00499680 for value+24h and node+38h, and
  00559280/0055A890 for value+6Ch and node+80h. An assignment is erase with
  `(out, {dst, [head]}, {dst, head})`, then copy `(dst, src)`. The dereference
  check asserts twice when node == head (006AA20C/006AA216). The iterator
  advances with 005540C0, and node, container and `this` are reloaded from the
  stack.
  - The only difference is direction. 006AA1C0 writes into the +6Ch value
    trees (source: the +8h node), and 006AA2D0 writes into the +8h node trees.
  - The packet brief called the two maps "swapped". In fact the walked map
    and the lookup map are the same in both functions; only source and
    destination change.

## Limits

- Which map is the live one is unproven, so the names give only the
  direction. The callers suggest +6Ch is a saved copy. 006AA1C0 is called from
  BSP_ControlBindingScreen_ListboxListener04 when a page opens. 006AA2D0 is
  called from ReloadInputConfig, OnRevertPromptResult and ConfirmOrNextDevice.
- The meanings of the fields are hypotheses: entry +D8h counters, +DCh
  "active", +BCh, the object kind +4, the binding slot kind 2, and screen
  +20h/+5Ch.
- 0048CBB0's AL is modelled as a bool. EAX's upper bytes are whatever
  LeaveCriticalSection left.
- The bodies take plain pointers. The existing seams use `Raw`/`Object`
  wrappers, and a host passes `.p` or the pointer. They are not ABI
  replacements, there are no EH frames (none in these bodies), and nothing
  has been game-validated.
