## Concrete guard defect and correction

`instantiate.py`, `root_recipe.py` and `root_gate.py` contain 12, 94 and 65 `assert`
nodes respectively, with no explicit rejection of optimized Python. The protocol
documents `python -B`, and the process runner inherits ambient `os.environ`.
`-B` does not prevent `-O`, `-OO` or `PYTHONOPTIMIZE` from removing assertions.
Receipt acceptance and identity checks, stage prerequisites and gate assumptions
can therefore disappear. This is a static defect, not a claim that the current
environment has optimization enabled; no bypass or selected helper was executed.

The normal inspected CLI has the correct review-before-launch order, but the
original `run_owned_process` gateway itself accepts arbitrary alphanumeric labels
and nonempty string argv, without independent receipt or dispatch authorization.
The requested strong guard must reject unlisted process requests at this gateway.
This is distinct from claiming the selected normal CLI secretly launches twice.

`local/dup57audit/proposal_strong/` contains the final review proposal for the three
execution modules. Each explicitly rejects nonzero `sys.flags.optimize` before
helper imports. Instantiator and recipe receipt/permission guards use conditional
exceptions instead of assertions. The subprocess gateway independently checks
the exact four compile labels, link, new gate builder and target-once argv;
requires accepted exact text; repeats linked manual acceptance for the target;
and rejects prior outputs/attempts. It records one effective environment with
inherited `PYTHONOPTIMIZE` removed and makes one explicit `shell=False` spawn.
The original environment is otherwise retained; this is not a hermetic Python
import or operating-system environment claim.

Independent AST inspection verifies the intended guards, dispatch and unchanged
function ASTs outside their bounded scopes. In particular the compile-stage,
launch, provider, gate-builder and post-reader logic is otherwise unchanged.
No proposed module was imported or executed. The first minimal `__debug__`
proposal and initial review are retained as unaccepted intermediate artifacts.
The strong proposal requires fresh exact selection pins and Root review; it is
not a receipt, instantiated fixture or observation of runtime behavior.
