# C04FD5 local contract with an opaque call

This is a conditional offline contract for the accepted nine bytes `6a00e88bffffff59c3` at saved listing C04FD5-C04FDD. It establishes the local transitions below; it does not establish a callable C++ ABI, a callee contract or runtime behavior. No new decoder, Native query, context query or target inspection was run.

**Mode and address conditions.** The decode assumes ordinary x86 32-bit code/default operands and the captured bytes actually being executed. These conditions do not establish SS.B. Saved listing coordinates are also separate from runtime addresses: assumption I says a listing address L equals its runtime linear instruction address. Only under I is `rho(L) = (L - CS.base) mod 2^32`; CS.base=0 is a second, sufficient assumption for numeric EIP=L. Without I, an established runtime mapping lambda(L) is needed instead. The Capstone target and saved control graph remain in listing coordinates.

The original pre-import manual used numeric return/target EIP values without explicitly recording those two address assumptions. This new qualification was reported to and accepted by Root before publication. It does not change the captured bytes, relative displacement, original manual, original decoder result or saved metadata. Neither runtime mapping nor CPU segment context has been verified.

**Entry and prefix.** Let entry ESP=S, stack segment=SS0, memory=M0 and all other input state be arbitrary. `Read32(M,SS,a)` and `Write32(M,SS,a,v)` address four bytes through the named stack segment and normal address translation; SS.base=0 is not required. Let R0 be the initial word at SS0:S, if readable. R0 is initially just a symbolic word, not a proven caller return address. Let rho be the near-return offset corresponding to listing C04FDC under the address mapping above. All full-ESP equations require SS.B=1, ordinary sequential state, valid accesses and normal instruction completion; additions are modulo 2^32.

| Local instruction | State transition under those conditions |
| --- | --- |
| C04FD5: `6A 00` | ESP=S-4; store sign-extended 32-bit zero at SS0:S-4. |
| C04FD7: `E8 8B FF FF FF` | ESP=S-8; store rho at SS0:S-8; transfer EIP to rho-117. |

The listing-coordinate target is C04FDC-0x75=C04F67. With listing/runtime identity and CS.base=0, rho=C04FDC and target EIP=C04F67. At callee entry, the local prefix places rho at ESP, zero at ESP+4 and the initial R0 at ESP+8, subject to the valid ordinary stack accesses above. Zero occupies an argument-shaped stack position; a formal argument, type or convention cannot be inferred from that layout. Initial register inputs such as ECX pass through this prefix and may matter to the callee.

**Opaque call and continuation.** C04F67 may change memory, stack, registers, flags, segments and modes, or may never reach the POP. If it does reach the captured C04FDC instruction, call its state C: ESP=T, SS=SSc, CS=CSc, memory=Mc, EAX=Ac and arithmetic flags=Fc. There is no established relation between T and S, Mc and M0/M2, Ac and entry EAX, or continuation and entry segments/modes. Apply the code, SS.B=1 and normal-completion conditions afresh to this state.

Let `V=Read32(Mc,SSc,T)` and `Q=Read32(Mc,SSc,T+4)`. The `59` POP sets ECX=V and ESP=T+4. The following `C3` near RET loads EIP=Q and sets ESP=T+8; it leaves CS=CSc and has no immediate extra cleanup operand. Thus the composed suffix is **ECX=V, EIP=Q, ESP=T+8**. The runtime linear destination also depends on CSc.base and valid target checks. EAX remains Ac, other general registers except ECX/ESP retain their continuation values, and the six arithmetic flags retain Fc; none of that proves preservation from entry. These instructions perform no explicit data-memory store. If the call never reaches the pair, this postcondition does not apply. C04FDE is an unqueried arithmetic end, not a fallthrough.

**A 16-bit stack is different.** With SS.B=0 and the independently assumed 32-bit operand mode, use SP and modulo-2^16 pointer updates while still transferring four-byte values. PUSH and CALL each subtract four from SP. At suffix entry SP=p, POP reads at p, RET reads at `u16(p+4)`, and final SP is `u16(p+8)`, provided each full memory access and instruction completes normally. The suffix preserves the continuation upper 16 bits of ESP during these SP updates; no carry into that half is implied. The near return still loads a 32-bit EIP. Neither that upper half nor the stack mode is assumed preserved across the call.

**What is not proved.** ECX=0 needs V=0; the earlier push does not fix the continuation pointer or protect that memory through the callee. A conventional one-near-return caller relation ESP_final=S+4 needs T=S-4, while returning to the original caller also needs Q=R0, a valid code-segment mapping and proof that R0 was the intended return offset. Calling this merely a balanced stack would hide those separate obligations. A return value needs Ac's semantics and a result convention; no local EAX write provides either.

For example, a hypothetical callee could return with T=S-4 after changing that stack word to a nonzero X, making ECX=X. A hypothetical callee that returns with an additional four-byte cleanup could instead leave T=S: the wrapper would pop R0 into ECX and return through the next word, ending at ESP=S+8 when valid. A callee could also fail to return. These are counterexamples to unsupported deductions, not observed target behaviors.

**Minimum obligations before implementation.** Establish arrival at the captured continuation in compatible byte/mode/segment/stack conditions. For an ordinary caller return, separately establish T=S-4, Q=R0 and the intended return mapping. Proving ECX=0 additionally requires V=0. A typed callable implementation further needs the actual parameter and hidden-register inputs, target effects, result type/convention, cleanup, nonvolatile-register requirements, stack alignment and any required exceptional/unwind behavior. An EAX result is possible only after establishing Ac and an EAX result convention. None of these callee obligations is asserted here.

**Saved metadata is a separate observation.** The accepted records show default/effective FALL_THROUGH for FD5 and FDC, UNCONDITIONAL_CALL to F67 with continuation FDC for FD7, and TERMINATOR with no fallthrough for FDD. Every override is NONE. The saved direct-target companion has name BSP_CRT_EncodePointerCurrentState, no_return=false and is_thunk=false. The name is an analysis identity; no_return=false and a saved call continuation do not prove an actual return, stack policy or semantic contract. RET's physical destination is the stack value Q even though the saved target list is empty.
