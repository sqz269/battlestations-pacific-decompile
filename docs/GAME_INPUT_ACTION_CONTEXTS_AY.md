# Shared game input action contexts (AY)

`GameInputActions` now exposes `binding_context()`, `configuration_context()` and `tick_context()` as mutable references to its existing `Impl` members. Its `unique_ptr<Impl>` keeps those members at stable addresses until the `GameInputActions` object is destroyed. The accessors allocate no replacement state and do not alter `update()`, `configure()` or `set_context_level()`.

The constructor binds the three members in order. The binding context borrows `GameInputRuntime::devices()` plus the supplied CRT and binding constants. The configuration context borrows `GameInputRuntime::records_context()`, **that same binding context**, and the timing globals. The tick context borrows `GameInputRuntime::backend_context().global_00f8bbf4`, the supplied callback and zero cells, the same timing globals, and its existing `Impl` call provider. Its poll callback uses the same binding member. Each existing public method resolves `GameInputRuntime::action_owner()` at call time and uses its corresponding member.

The full configuration route can pass `configuration_context()` to `NativeInputConfigurationParseServices::actions` and `tick_context()` to `NativeInputConfigurationRuntimeServices::tick`. The parse action activation therefore reaches the same records, devices and timing as direct `configure()`, while the loader's rebind/update tail reaches the same backend and callback as direct `update()`. `binding_context()` is available to other binding consumers and is identical to the reference already stored inside the configuration member. `NativeInputSettingsDefaultsServices` separately borrows the same runtime action-owner/backend publications and a keyboard application for the same settings receiver; it does not itself take one of these three context types.

This change makes context sharing source-callable. The executable still lacks the actual game+3C configuration owner, raw Lua/settings graph, settings/defaults/keyboard service composition, and callback/game deadline publications described in `NATIVE_INPUT_HOST_INTEGRATION_GAP_AX.md`. No production loader call or gameplay route is claimed. All borrowed `GameInputRuntime` and service cells must outlive `GameInputActions`, and consumers must not retain these references after its destruction.
