# CC12 allocation-stats raw lifecycle Source

This packet implements three standalone MSVC Win32 Source functions: base destruction **00BE27F0**, base scalar deletion **00BE2890**, and scalar deletion **00BE2930**. All six candidate/provider translation units compile with the recorded Release flags. The complete Source object audit confirms the required observation, cleanup and free order. **00BE28E0 is excluded.** CMake registration and the normal integrated build belong to the primary integrator.

The implementation reuses `NativeAllocationStatsConstructorContext`. It borrows the actual manager and allocation-stats publication cells, creates no owner/cell, and calls existing genuine providers. It does not replace startup's semantic `AllocationStatsState` or install a profile deletion binding.

## Source behavior

`destroy_native_allocation_stats_base_00be27f0` writes D685E0 before its Source base-cleanup lifetime begins. It calls genuine `get_native_singleton_manager_00415350`, captures the first manager's actual +10h section, initializes an actual eight-byte CE37FC/section guard, and conditionally enters/increments the section's DWORD at +18h. Guard cleanup is armed only after those operations complete.

It obtains the second manager before reloading the current actual stats publication, then calls genuine `unregister_native_singleton_object_00bcfca0` with that second manager/current publication. Only a normal return permits the publication clear. Normal release decrements/leaves the first captured section while guard cleanup remains armed. Genuine `destroy_native_generic_singleton_base_00412430` resets the captured receiver to CE3818 last. The current publication is not assumed to equal the receiver, and the two manager observations are not assumed equal. Receiver +4/+8 are untouched.

Before guard arming, escaping C++ execution invokes the base reset. After guard arming, genuine `destroy_native_singleton_guard_00411ee0` receives the actual local guard; its ordinary return allows the base reset. It reads the guard's current +4 section before its profile stamp, rather than receiving a stale section copy. Completed unregister/clear/depth effects remain. There is no retry, rollback, failure-path publication clear or receiver free. A C++ exception escaping guard cleanup is explicitly terminated by the Source wrapper; other exception codes continue search. The base reset and free provider are `noexcept`. These are Source language/runtime policies, not recovered Native cleanup-failure handling.

Both scalar APIs call this base destructor directly, inspect only flags bit0 after its normal return, conditionally invoke genuine `singleton_lifetime_free` on the original receiver and return that address. BE2930 does not introduce a separate derived-complete-destructor claim. An escaping destructor prevents the free. The getter retains its existing lazy manager allocation behavior; no receiver allocation policy is introduced.

The caller retains valid, aligned 12-byte receiver storage, two distinct fixed publication-cell bindings, valid actual managers/vector storage, and captured section storage through every call and required cleanup. These regions and context must satisfy the constructor header's disjointness/lifetime rules; conflicting concurrent accesses and provider-induced invalidation are excluded. Scalar bit0 requires storage compatible with the genuine allocator/free family. Profile values are retained identity DWORDs, not rebuilt callable virtual tables.
