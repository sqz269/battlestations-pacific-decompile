1. Loads the current publication, dereferences its current profile pointer, reads that table's current `+4` target, and calls `allocation_metric(target, captured_owner)` before reading the current resource factory.
2. After parsing/cache insertion and clearing manager+20, reloads the current stats publication and current profile/slot4, then invokes the metric again.
3. Stores the wrapping unsigned starting-minus-ending result into the **current** manager+24 resource at +40.

There is no null gate, synthetic owner, lazy stats construction or cached owner/table/metric snapshot in this path. A cache hit returns before either stats query; it still preserves the existing factory publication and resource retain. ## Retained Native evidence: what it proves

The cached startup listing at `0073D45D..0073D47D` pushes `0xC`, calls `BF681B`, preserves the allocation pointer and arms its existing caller state, then calls `BE2900` only for a nonnull allocation. The original call is application phase0, before the frame-clock/VFS sequence; it is not evidence of a new CRT position. Its allocation-failure cleanup handler was not queried in this packet.

The retained `BE2900` listing is nine ordinary instructions: preserve ESI, capture incoming ECX, call `BE2750`, stamp profile `D685F4`, store `0x40000000` at +4, store zero at +8, return the same receiver. It supplies an exact normal-path three-word storage shape. The existing semantic Source fragment omits the base operation and profile. Cached metadata also lists `BE27F0` as a callee, but that is **not** a direct call in this retained ordinary listing; the listing, not that aggregate metadata, defines the observed sequence.

The retained `BE2750` normal listing shows:

* Stamp the receiver with the intermediate `D685E0` profile.
* Resolve the actual singleton manager and capture its +10 critical-section pointer.
* Enter that captured section and increment its +18 recursion word when nonnull.
* Publish the receiver to actual `0109CEFC`.
* Resolve the manager again, then reload **current `0109CEFC`** and register that value through `BD0C30`.
* Decrement and leave the originally captured section, restore its exception chain and return the receiver.

## Existing services that a later owner can reuse

The actual `GameSingletonHost::sound_lifetime()` borrows the canonical process manager publication `01090AA0`. `SoundLifetimeAccess` already resolves the current raw manager; `SoundLifetimeManagerView` already binds genuine raw `BD0C30` registration and `BCFCA0` removal. `CapturedSoundLifetimeSection` already captures one manager's actual +10 section and adjusts that section's +18 recursion word on entry/exit, even if publication values change. These services introduce no private manager, lock or counter. The constructor still needs its own verified ordinary exception schedule around them.

`singleton_lifetime_allocate` is the existing explicit `BF681B` Source allocation boundary: malloc/new-handler retry or `bad_alloc`; `singleton_lifetime_free` uses the matching canonical free boundary. The observed raw owner allocation is twelve bytes. A future manager-registered owner must use storage compatible with its verified scalar-free path; registering the present stack-local semantic state, or embedding raw owner bytes in an unrelated C++ member and later freeing that member, is not a valid substitution.

The allocation budget/startup words and manager-lock recursion word are distinct from the type-ID counter `0109DB7C`. None of the retained stats constructor/metric evidence consumes a type ID. Sharing the same singleton manager does not turn allocation statistics into the fallback type counter domain.

Original table storage is already available through the existing mapped-data service. `game_main` requests the `D60000` 64-KB band, which contains `D685E0/F4`. `GameNativeReadOnlyData` verifies the supported image before mapping read-only/non-executable pages and exposes `data_at`; it explicitly supplies no mutable globals or object owners. This is Source capability/lifetime evidence, not a new execution or fresh installed-byte verification. A future binding must validate and borrow the actual mapped spans and dispatch numeric targets through genuine Source; the numeric table entries are never executable Source function pointers.

The canonical mapped-data owner is retained beyond `host.reset()`. `GameStartupHost` retains raw-service/publication contexts through the singleton drain, and `GameSingletonHost::shutdown` captures the actual manager, drains it, frees it, then clears that same manager publication. New allocation-stats publication and deletion bindings must survive both the normal and fallback drain. They must exist **before** the base constructor can publish/register the owner, including a partially initialized base-profile owner on an exceptional path if the recovered contract leaves one registered.

Current `delete_current_profile` has no `D685E0` or `D685F4` case and rejects an unbound profile. The raw drain pops an entry before dispatching its current profile with flags1; its ordinary exception scope clears the manager's remaining storage. Consequently, registration without a genuine stats deletion binding would enter an already-demonstrated unsupported path. Mapping the table or supplying the known metric body does not close that path.
