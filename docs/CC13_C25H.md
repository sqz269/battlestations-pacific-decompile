# cc13-c25h: the [unit+C25h] early return in 009C18C0

Packet cc13-c25h, from rev4's note N2 on cc13-mvspeed. Names are hypotheses, not recovered symbols.
No game runs. Logs: the current-main OFF runs of 2026-10-19 in the cc9-lua52 tree
(`l70r_n_*_main_ref.log`, `l70r_vos17_main_ref.log`).

## Verdict

**The branch is not reached in any logged mission, so no switch was built.**
- No unit that released a torpedo ever ran the torpedo moveto state: USN21 and USN01 each have
  none.
- The level bomber never re-enters moveto.
- The drop kamikaze re-enters moveto at least 14.7 s after its release. The image's C25h is clear
  within about 2.5 s of the release (see below).

## The branch (bytes)

009C18C0, after the speed slot call at 009C198A-009C1999:
- **009C199B-009C19AB:**
  - It reads EBX = [[state+4]+4], the unit.
  - It tests `CMP byte [EBX+C25h],0`.
  - It jumps to 009C19E7 (the target test) when the byte is 0.
- **009C19AD-009C19E4, the byte set.** The command block is cmd = [[state+4]+18h]. The tick
  stores:
  - cmd+2BCh = 0.0 (009C19B5);
  - cmd+2D0h = 2 (009C19BD);
  - cmd+2C4h = 0.0 (009C19CE);
  - cmd+2CCh = 1 (009C19D6).
  Then it returns (009C19E4 RET 4).
- **What the early return skips:** the target test and everything after it. That is the glide
  (009FBA50), the heading (009F9E40), the gun cone and the direction call (009FABE0).
- **Same stores as the no-target tail 009C1B69-009C1BB1, with one exception.** The no-target
  tail also sets approach+10h->+7Ch = 1 (009C1BA8). The C25h branch does not.
- **The moveto speed is still written.** The branch comes after the unconditional speed call.

These are the same four stores that the moveto state tick 009C2430 and the circle tick 009C26D0
make under the same test. The host already models those two as `kMoveToC25ArmBound` (ON,
`moveto_c25_arm`, game_hosts_units.cpp).

**A doc correction.** docs/BOT_TASK_STATES.md (the 009C18C0 table, step 3) says the C25h branch
"writes nothing more". It writes the four stores above.

## What sets and clears unit+C25h

- **Set:** 007C0EE2 `MOV byte [EBP+C25h],1`, in 007C0D90's rack walk, whenever the walk fired a
  rack.
  - 007C0D90 is called at 007CEA8D, in the plane step 007CE040's release issue stage (the block
    from 007CE9FD, `plane_release_issue_stage_007ce9fd` in the host). That happens
    when unit+C20h (issue requests) is above 0 and the interval timer unit+C28h has gone
    negative.
  - The requests come from 007BBBA0. Its callers are the task's release and 0099B6CD (the
    torpedo arm's fall-through for wingmen holding unit+C58h orders).
  - A rocket rack also raises the byte (007C0EEB returns before the orders).
- **Cleared:** at 007CEB22 (ESI = unit+310h, so [ESI+915h] is unit+C25h), when all of these
  hold. The stage's gates come first (007CE9FD-007CEA72); if any fails, the stage does nothing
  that step:
  - the lobby mode [[00E188A8]+1FE4h] is not 2;
  - the unit+9E0h byte is clear;
  - +C3Ah is clear;
  - +5Dh is clear;
  - +900h is 4, 5, 6 or 7;
  - the decremented timer is below 0 (007CEA72) before the -1.2 test.
  Then the cleanup arm's own conditions:
  - C20h is 0;
  - the decremented timer is below -1.2 (00D05EA4, 007CEAD7 COMISS);
  - no device in unit+974h's list answers vtable +1FCh (busy), 007CEB00-007CEB1D.
- **Lifetime:** after the last issue the timer is re-seeded with the issue interval times
  BombDelay. So the byte stays set for that interval plus at least 1.2 s.
- A blocked clear parks the timer at [00CE69D0] (007CEAEE) and retries.

The host keeps the byte as `torpedo_release_pending_c25`:
- Set at the 007C0EE2 point: the torpedo and level-bomb device walk at game_hosts_units.cpp,
  around line 33834, and `set_release_pending_c25` in src/torpedo_release_orders.cpp.
- Cleared by the bound 007CE9FD stage (src/torpedo_issue_timing.cpp, `clear_release_pending_c25`).

The drop kamikaze uses a one-think stand-in, `dkz_c25`, instead.

## Is it reachable for a torpedo plane?

The torpedo task runs 009C18C0 only in its moveto state: the state chooser 009D4030 picks moveto
when the unit has no follow target. The follow state runs 009C1FD0. The byte can be set during
moveto in two ways:
1. **Abort after a drop.** The plane releases in aim (aim goes to goaway), and the engagement
   test 009D3210 then fails within the byte's lifetime, for example because the target is lost.
   009D4053 returns to the approach state, which is moveto for a flight leader.
2. **Fall-through release.** The 009D49A0 arm falls through to 0099B6A0 for a non-engaged task
   that holds C58h orders. In that case 007BBBA0 can release while the state is moveto. In
   practice only members get the orders (007EEF30 hands them to the other members), and a member
   flies follow, not moveto.

**The logs.** local/c25_units.py reads the per-unit `arm_ticks ... states[...]` summaries. Those
are printed only for units still alive, so it undercounted. The counts below are rev4's:

| mission | torpedo droppers | visited moveto |
| --- | --- | --- |
| USN21 (l70r_n_vu21_main_ref) | 4: Intrepid_sqn31\|.-III, Intrepid_sqn31\|.-II, Intrepid_sqn31, Cabot_sqn56\|.-III. Three died 3 to 6 s after their drop (783.78, 784.18, 1074.07) | no |
| USN01 (l70r_n_u1s_main_ref) | 4 arm releasers (KatTBD x3, ConTBD2\|.-III) plus a ConTBD1\|.-II drop | no torpedo arm shows `moveto=` |
| l70r_n_j6k_main_ref, l70r_n_u15e_main_ref | 0 | |

**Reach is zero in these logs, but not structurally zero.** Intrepid_sqn31 is a flight leader,
so it is exactly the path-1 candidate: its approach state is moveto. It is safe here only because
it died a few seconds after its drop. A leader that survives a drop and loses its engagement
within the byte's lifetime (about the issue interval plus 1.2 s) would run the branch.

**The drop kamikaze case is settled: C25h is clear long before the re-entry.**
- **The busy answer is "still dropping", not a latch.**
  - The rack's vtable +1FCh is 006E3CD0, `MOV AL,[ECX+498h]` (dropBombs), for an MBombPlatform.
    A multiple platform's is 006E4360, `XOR AL,AL` (never busy).
  - 006E3550 (+1F0h, the fire) raises dropBombs. The rack's own tick 006E56F0 clears it at
    006E58E1 once `CanFire(1)` fails with the ammo spent, and at 006E5880 for a non-plane owner.
    See docs/PLANE_DEVICE_WALK.md, "Correction, 2026-09-26". The host already answers this way
    (`plane_device_walk_007ceb00` in game_hosts_units.cpp).
  - **Every device in the list uses one of those two bodies.** The list unit+974h (ESI+664h) is
    filled by 007CDF20 (at creation) and 007BCB30 (at re-equip), and only with children that
    answer IsKindOf(25h). Class 25h is MBombPlatform, and its only subclass is
    MMultipleBombPlatform 26h (docs/PLANE_DEVICE_WALK.md, "The list"; docs/ENTITY_CLASS_IDS.md).
    So busy is bounded by the drop.
  - The drop kamikaze carries one round (`rounds_left=0` on every release line), so its rack
    stops answering busy on the tick after the drop.
- **The clear runs.**
  - After the drop the plane is in free flight, control mode 7, which 007CEA33 admits.
  - With C20h at 0, the stage clears C25h at 007CEB22 once the timer is below -1.2. The timer
    was re-seeded at the issue with the interval U(0.9, 1.1) × BombDelay. BombDelay is 0 to 0.5
    in this installation (docs/PLANE_FLIGHT_NATIVES.md).
  - A blocked try re-parks at -0.5, which costs 0.7 s more.
- **The bound.** The byte is clear within about 1.1 × 0.5 + 1.2 + 0.7 ≈ 2.5 s of the release.
  The earliest logged re-entry into moveto is 14.7 s after it.
- **If the walk fires nothing.** If the walk at 007C0D90 does not fire the round's rack (no
  IsKindOf(25h) or no 2Ah answer), 007C0ED9 returns before 007C0EE2 and C25h is never set at all.
- **Caveat.** The stage gates listed under "Cleared" (lobby mode, +9E0h, +C3Ah, +5Dh) were
  assumed to pass in normal flight.

## Status

Read from bytes and documented. No code change. No switch, because nothing is reached in the
logged missions. If a switch were wanted, the faithful form is `moveto_c25_arm` applied after the
speed write at every 009C18C0 site, guarded by `torpedo_release_pending_c25`.
